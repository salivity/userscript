Purpose of @connect Directive in Userscripts

The @connect directive in userscripts is a security feature used by script managers like Tampermonkey, Violentmonkey, and Greasemonkey to restrict which external domains a script can communicate with using cross-origin request APIs. By requiring developers to explicitly declare target domains, the directive prevents malicious scripts from silently exfiltrating sensitive user data, contacting unauthorized servers, or performing unauthorized cross-site requests.

Understanding the Need for Security in Userscripts

Userscripts run directly within the context of your browser and often possess elevated privileges compared to normal web pages. Standard browser security enforces the Same-Origin Policy (SOP), which prevents web pages from freely making requests to different domains.

To allow useful features—such as fetching price comparisons, pulling external API data, or downloading media—userscripts use custom APIs like GM_xmlhttpRequest or GM.xmlHttpRequest. Because these APIs bypass standard browser CORS restrictions, strict control mechanisms are necessary to prevent abuse.

Core Functions of the @connect Directive

The @connect directive serves three main security and functional purposes:

1. Explicit Domain Whitelisting

Developers use @connect in the metadata block to define the exact hostnames, domains, subdomains, or IP addresses the script intends to contact.

Common declaration formats include:

  • // @connect example.com – Allows connections to example.com and its subdomains.
  • // @connect api.example.com – Restricts connections specifically to api.example.com.
  • // @connect self – Restricts connections to the domain of the current page the script is running on.
  • // @connect * – Allows connections to any domain (typically discouraged for security reasons).

2. User Permission Management and Transparency

When a script attempts to make a network request via GM_xmlhttpRequest:

  • If the target domain is listed in the @connect manifest, the userscript manager validates it against the user's settings.
  • If the target domain is not listed, the manager intercepts the request and prompts the user with a security dialog, asking whether to allow or block the connection.

This transparency ensures users are informed before any unexpected background traffic occurs.

3. Preventing Data Exfiltration

Without @connect enforcement, a compromised or malicious script could read sensitive information from a logged-in session (such as tokens, personal details, or cookies) and send it to a remote attacker-controlled server in the background. Restricting destination hosts mitigates this risk significantly.

Best Practices for Using @connect

  • Be Specific: Always list exact domains rather than broad wildcards (*) to maintain strong security defaults for users.
  • Declare All Destinations: Include primary APIs, fallbacks, and content delivery networks (CDNs) that the script relies on.
  • Respect User Choice: Avoid attempting to bypass security prompts if a user denies access to a specific domain.
