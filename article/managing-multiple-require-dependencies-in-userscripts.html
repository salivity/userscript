Managing Multiple @require Dependencies in Userscripts

Userscript managers such as Tampermonkey, Violentmonkey, and Greasemonkey handle external JavaScript dependencies using the @require metadata directive. When a userscript specifies multiple @require tags, the script manager fetches and caches all declared libraries at installation, then executes them synchronously in the exact order they appear in the metadata block before running the main script.

Execution Order and Synchronous Loading

Userscript managers process @require directives sequentially from top to bottom. This strict ordering is critical when managing libraries that rely on one another.

For example, if a script relies on a framework and a plugin built for that framework, the framework must be listed first:

// ==UserScript==
// @name         Dependency Example
// @namespace    http://example.com/
// @version      1.0
// @match        https://example.com/*
// @require      https://code.jquery.com/jquery-3.6.0.min.js
// @require      https://cdnjs.cloudflare.com/ajax/libs/jquery-toast-plugin/1.3.2/jquery.toast.min.js
// ==UserScript==

In this setup, the manager guarantees that jQuery loads and attaches itself to the environment before the toast plugin runs. If the order were reversed, the plugin would fail because jQuery would not yet exist.

Caching and Installation Lifecycle

Unlike standard web pages that fetch script tags over the network on every page load, userscript managers fetch @require dependencies only when the script is installed or updated.

  1. Download: The user installs the script, and the manager downloads the user script and all linked @require files.
  2. Storage: The raw source code of each dependency is stored locally in the extension's local storage.
  3. Execution: On matching web pages, the manager injects the cached source code of each @require file sequentially, followed by the main userscript.

Because libraries are cached locally, network latency does not delay individual page loads, and scripts can function offline after initial installation. If a @require URL fails to download during installation, the script installation will fail entirely.

Scope and Context Injection

Required scripts execute within the same context as the main userscript. Depending on the @grant settings used in the metadata block:

  • Sandboxed Context (@grant set to specific APIs): The required libraries execute within a isolated sandbox context (e.g., GM context). Global variables defined by required scripts (like $ or lodash) are attached to the sandbox's global scope, making them accessible to subsequent required scripts and the main script, but hidden from the underlying web page.
  • Page Context (@grant none): The required libraries and the userscript execute directly in the page's standard window context, sharing scope with the host website.

Managing Conflicting or Duplicate Dependencies

The @require directive does not feature modern package management capabilities like automatic deduplication or semantic version resolution found in tools like npm.

  • No Automatic Resolution: If two required libraries internalize different versions of the same third-party utility, both will execute and potentially overwrite global variables unless the libraries use unique namespaces or non-conflicting builds.
  • Scope Pollution: Libraries that attach properties to window or globalThis will overwrite existing values if executed later in the @require chain.

To prevent scope conflicts, developers should ensure that required libraries do not conflict in namespace or explicitly use libraries designed to operate within isolated environments.
