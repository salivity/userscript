Can Userscripts Modify Shared Workers?

Userscripts cannot directly inject code into or alter the internal memory of an active Shared Worker because workers run in an isolated background scope separate from the main window context. However, userscripts can effectively control and modify the behavior of Shared Workers by monkey-patching the global SharedWorker constructor in the web page before the worker is instantiated, allowing full interception and manipulation of all incoming and outgoing messages.

Understanding the Architecture Barrier

A Shared Worker runs in a SharedWorkerGlobalScope, which is entirely detached from the page's window object and DOM context. Standard userscript managers (such as Tampermonkey or Violentmonkey) execute scripts within the context of the web page or in an isolated content script environment.

Because of this separation:

  • Userscripts cannot access worker variables directly.
  • Userscripts cannot execute arbitrary code inside the worker thread.
  • DOM manipulation within the worker thread remains impossible.

Intercepting Shared Workers via Monkey-Patching

While direct script injection inside the worker thread is restricted, userscripts execute early enough in the document lifecycle to redefine how the browser handles the creation of SharedWorker instances.

By overriding window.SharedWorker in the page context before the web application initializes its background worker, a userscript can intercept the communication channel (MessagePort).

How the Interception Works

  1. Constructor Overriding: The userscript replaces window.SharedWorker with a custom proxy function.
  2. Port Wrapping: When the web application instantiates a new SharedWorker(), the custom proxy creates the genuine worker but wraps its MessagePort.
  3. Message Manipulation: The userscript hooks into port.postMessage and port.onmessage listeners.
// Example of intercepting a Shared Worker in a userscript
const OriginalSharedWorker = window.SharedWorker;

window.SharedWorker = function(scriptURL, options) {
    const workerInstance = new OriginalSharedWorker(scriptURL, options);
    const originalPostMessage = workerInstance.port.postMessage;

    // Intercept messages sent FROM page TO worker
    workerInstance.port.postMessage = function(data) {
        console.log('Outgoing data intercepted:', data);
        // Modify data here if needed
        originalPostMessage.apply(workerInstance.port, [data]);
    };

    // Intercept messages sent FROM worker TO page
    workerInstance.port.addEventListener('message', (event) => {
        console.log('Incoming data intercepted:', event.data);
    });

    return workerInstance;
};

Technical Limitations

  • Execution Timing: The userscript must run at document-start or before the web application creates the SharedWorker. If the worker is instantiated before the userscript loads, existing communication channels cannot be retroactively intercepted.
  • Same-Origin Policy: Shared Workers strictly enforce same-origin policies. A userscript cannot redirect a Shared Worker to a script hosted on an external domain unless proper CORS headers are present.
  • Worker-Initiated WebSockets: If the Shared Worker opens its own WebSocket or fetch connections directly from the background thread, the userscript cannot intercept those network requests using standard main-thread overrides.
