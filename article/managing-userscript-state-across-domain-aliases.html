Managing Userscript State Across Domain Aliases

Managing state persistence across different domain aliases poses a challenge due to browser same-origin policies, but userscripts overcome this by leveraging script manager storage APIs or cross-domain messaging. Standard browser storage solutions like localStorage restrict data access to a single domain, causing user settings or authentication tokens to fragment when navigating across mirror sites or domain aliases. This guide explains how developers utilize userscript-specific storage functions, cross-domain request APIs, and message-passing techniques to maintain seamless, unified application state across multiple domains.

The Web Storage Isolation Problem

Standard web storage mechanisms—including localStorage, sessionStorage, and IndexedDB—are bound strictly to the browser's Same-Origin Policy. If a userscript runs on both domain-alias.com and domain-alias.org, changes made to localStorage on one domain are completely invisible to the other. Relying on standard web APIs forces users to re-authenticate or re-configure script settings every time they switch between domain aliases.

Using Built-in GM Storage APIs

The primary and most efficient method to achieve cross-domain state persistence is using the userscript manager's built-in storage APIs. Storage provided by extensions like Tampermonkey, Violentmonkey, or Greasemonkey operates within the extension's privileged context rather than the web page's origin.

To share state across domain aliases using built-in storage:

  1. Declare Grants: Include @grant GM_setValue and @grant GM_getValue (or the modern asynchronous equivalents @grant GM.setValue and @grant GM.getValue) in the metadata block.
  2. Define Target Domains: List all domain aliases using @match or @include rules in the script header.
// ==UserScript==
// @name         Cross-Domain State Sync
// @match        https://example.com/*
// @match        https://example.org/*
// @grant        GM_setValue
// @grant        GM_getValue
// ==/UserScript==

// Save state on any matched domain
GM_setValue('userPreferences', { theme: 'dark', autoSave: true });

// Read state on any matched domain
const preferences = GM_getValue('userPreferences', {});

Because GM_setValue binds data directly to the installed userscript instance rather than the active website's origin, the stored data remains identical across every domain specified in the script's header.

Cross-Domain Messaging with PostMessage

When a userscript interacts with web applications that run in isolated frames across different domain aliases, developers combine window.postMessage with GM storage APIs to relay state changes.

  • Iframe Bridge Pattern: A script running on an alias domain creates or targets an iframe hosted on the primary domain.
  • Communication Channel: The script uses postMessage to request or send state updates to the iframe.
  • Origin Verification: To prevent security vulnerabilities, developers verify event.origin inside the message event listener before updating the script state.
window.addEventListener('message', (event) => {
    const trustedOrigins = ['https://example.com', 'https://example.org'];
    if (!trustedOrigins.includes(event.origin)) return;

    if (event.data.type === 'GET_STATE') {
        const state = GM_getValue('appState');
        event.source.postMessage({ type: 'STATE_RESPONSE', state }, event.origin);
    }
});

Remote State Synchronization via Centralized Endpoints

When state must persist across different browser instances or devices in addition to domain aliases, developers sync state with a remote server using GM_xmlhttpRequest.

Standard web fetch operations are subject to Cross-Origin Resource Sharing (CORS) restrictions. GM_xmlhttpRequest bypasses browser CORS limits, allowing the userscript to communicate directly with a centralized backend endpoint regardless of the current domain alias.

Best Practices for Cross-Domain Userscript State

  • Key Prefixing: Namespace storage keys (e.g., app_v1_settings) to prevent naming collisions across script updates.
  • Data Sanitization: Parse and validate any retrieved state data before injecting it into the page DOM to protect against Cross-Site Scripting (XSS).
  • Strict Header Matching: Limit the @match directives strictly to verified domain aliases to avoid exposing sensitive stored state to unauthorized third-party sites.
