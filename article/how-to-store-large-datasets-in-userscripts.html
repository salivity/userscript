How to Store Large Datasets in Userscripts

Userscripts often require persistent storage to handle complex tasks, cache external APIs, or process large offline datasets. While simple key-value APIs like standard browser storage work for small amounts of text, larger datasets demand more robust solutions to avoid quota limitations and browser performance degradation. This guide evaluates the best local storage methods for userscripts—including IndexedDB, the script manager's native GM storage API, and the Origin Private File System—detailing their capacities, performance characteristics, and practical implementation scenarios.

1. IndexedDB: Best for Structured and Bulk Data

IndexedDB is a low-level, object-oriented database built into modern web browsers. It is the best option for userscripts handling megabytes or gigabytes of structured data on a specific domain.

  • Capacity: Dynamic, usually allowing up to 20% to 50% of available disk space per origin.
  • Performance: Fully asynchronous operations prevent the main thread from freezing during heavy read or write operations.
  • Data Types: Natively supports objects, arrays, blobs, typed arrays, and files without requiring manual JSON stringification.
  • Best Use Case: Storing thousands of JSON records, heavy search indexes, or cached API responses.

To simplify IndexedDB syntax inside a userscript, lightweight wrapper libraries like idb-keyval or Dexie.js can be included using the @require directive in the metadata block.

2. GM_setValue and GM.setValue: Best for Cross-Domain Data Access

Standard browser APIs isolate data to a single origin (domain). The extension-provided userscript storage API (GM_setValue or GM.setValue) stores data directly within the script manager (such as Tampermonkey, Violentmonkey, or Greasemonkey).

  • Capacity: Varies by script manager and user settings, but typically supports tens of megabytes comfortably.
  • Key Advantage: Data persists across different websites and domains, allowing scripts running on Site A to access data generated on Site B.
  • Data Types: Handles primitives, objects, and arrays (automatically serialized by modern managers).
  • Best Use Case: Global application state, cross-site user settings, and shared caching across multiple domains.

3. Origin Private File System (OPFS): Best for High-Performance Binary Data

The Origin Private File System provides access to a private, highly optimized virtual file system tied to the origin of the host page.

  • Capacity: Large storage quotas similar to IndexedDB.
  • Performance: Delivers near-native read and write speeds, especially when operated within Web Workers using synchronous file handles.
  • Data Types: Raw binary data, ArrayBuffers, Blobs, and large streamable files.
  • Best Use Case: Local AI/ML model storage, WebAssembly databases (such as SQLite WASM), and large media file caching.

4. Web Storage API (LocalStorage): Limited to Small Datasets

While window.localStorage is simple to use, it is not recommended for large datasets.

  • Capacity: Hard cap of 5MB to 10MB per origin.
  • Performance: Synchronous operations block the main execution thread, causing page lag during bulk operations.
  • Data Types: Accepts plain text strings only, requiring heavy JSON parsing for complex data structures.
  • Best Use Case: Small user preferences, UI toggle states, or simple session identifiers.

Storage Method Selection Summary

  • Select IndexedDB for single-site scripts that need to store large, queryable, or structured JSON datasets.
  • Select GM.setValue when data must be accessed across different domains or shielded from host page scripts.
  • Select OPFS (or SQLite WASM) for heavy binary processing, local database queries, or files over several hundred megabytes.
