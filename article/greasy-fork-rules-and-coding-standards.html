Greasy Fork Rules and Coding Standards

Hosting userscripts on Greasy Fork requires adherence to specific rules designed to ensure security, transparency, and user safety. While the platform does not enforce strict code formatting or stylistic conventions, it imposes strict technical and functional guidelines. This article covers the essential requirements for publishing userscripts on Greasy Fork, including rules on code readability, external resources, user privacy, and intellectual property.

Code Transparency and Obfuscation

The most critical technical requirement on Greasy Fork is code readability.

  • No Obfuscation: Code must not be obfuscated, minified, or hidden in any way. Reviewers and users must be able to inspect and understand what the script does.
  • Source Code Availability: If a script is compiled from another source language (such as TypeScript, CoffeeScript, or Babel-transpiled code), the original, uncompiled source code must be provided or linked appropriately according to Greasy Fork's development rules.

External Resources and Dynamic Code

Greasy Fork strictly limits how scripts load external files to prevent malicious code injection.

  • Allowed Loading Methods: External libraries must be loaded using the standard UserScript metadata keys, specifically @require or @resource.
  • Approved CDNs: External libraries loaded via @require must come from trusted, secure Content Delivery Networks (CDNs) or Greasy Fork itself.
  • No Remote Code Execution: Scripts cannot fetch executable JavaScript via fetch(), XMLHttpRequest, or eval() from external sources at runtime. All executable code must be contained directly within the script or declared in @require.

Security and Privacy Requirements

Scripts must respect the host environment and the user's data.

  • No Malicious Behavior: Scripts that perform unauthorized tracking, credential harvesting, unauthorized ad insertion, drive-by downloads, or DDoS attacks are strictly banned.
  • Data Collection Limits: Scripts must not collect sensitive personal data without explicit user consent. Tracking telemetry must be minimal, optional, and clearly disclosed in the script's description.
  • Proper Metadata Scope: The @match and @include rules in the metadata block must be scoped appropriately. Broad wildcard matches like @match *://*/* are discouraged unless the script genuinely functions on all websites.

Metadata and Documentation Standards

Greasy Fork parses the standard metadata block at the top of the script to generate the listing page.

  • Accurate Information: The @name and @description tags must accurately convey what the script does. Using misleading names to attract downloads is prohibited.
  • Localization: If translations are provided via @name:lang or @description:lang, they must accurately reflect the localized functionality.
  • Version Control: Scripts must use valid semver-style versioning (@version) so the platform can manage automatic updates for users.

Spam, Quality, and Licensing

  • Functionality: Scripts must serve a functional purpose. Blank scripts, non-working scripts, or scripts designed purely to advertise a website or service will be removed.
  • Intellectual Property: You must own the rights to the code or comply with the license of the original author. If you fork an existing script, you must retain the original license, give proper attribution, and respect copyright terms.
  • Duplication: Uploading duplicate scripts or artificially inflating download counts through automated means leads to account suspension.
