How to Share Code Between Multiple Userscripts

Sharing code logic between multiple related userscripts improves maintainability, reduces code duplication, and streamlines updates across your scripts. This guide outlines the most effective techniques for modularizing and reusing logic across Tampermonkey, Violentmonkey, or Greasemonkey scripts. You will learn how to leverage metadata directives, modern build tools, shared storage, and browser-level APIs to keep your codebase clean and scalable.

Use the @require Metadata Directive

The standard way to share utility functions or complex libraries across userscripts is through the @require header directive.

  • External Hosting: Host your shared JavaScript functions on a CDN, GitHub, raw Gist, or local development server.
  • Metadata Configuration: Add @require https://your-domain.com/shared-logic.js inside the ==UserScript== block of each dependent script.
  • Execution Scope: The script manager downloads, caches, and executes the required file before running your main userscript, making all global functions inside the required script available immediately.

Modularize and Bundle with Vite or Webpack

For local development across a complex suite of scripts, relying solely on @require can hinder rapid iteration. Using a module bundler like Vite, Webpack, or Rollup offers a superior workflow.

  • Shared Source Directory: Structure your project as a monorepo or standard project folder with a dedicated src/common/ folder containing shared modules.
  • ES Imports: Import utility functions directly into script entry points using standard syntax (import { formatData } from '../common/utils.js').
  • Automated Compilation: Configure the bundler to output compiled .user.js files. The bundler automatically embeds only the necessary shared code into each final output script.

Create a Core Controller Script via Window Objects

If your related userscripts execute on the same website domain, you can create a "Core" userscript that acts as an API provider for secondary scripts.

  1. Initialize Core Script: Set the core script to run early using @run-at document-start.
  2. Expose Namespace: Attach your shared functions to window or unsafeWindow under a distinct namespace (e.g., window.MyScriptCore = { ... }).
  3. Execute Secondary Scripts: Set secondary scripts to run later (e.g., @run-at document-idle), allowing them to invoke functions directly from window.MyScriptCore.

Share State and Cache with Storage APIs

Sharing logic frequently requires sharing current state, user settings, or cached network requests between scripts.

  • Extension Storage: Use GM_setValue and GM_getValue to read and write shared variables securely across pages if supported by your script manager.
  • Web Storage API: Use window.localStorage or window.sessionStorage for lightweight, synchronous data sharing on identical domains.
  • Storage Event Listeners: Listen to state updates across scripts in real time using window.addEventListener('storage', callback).

Essential Maintenance Best Practices

  • Namespace Global Variables: Wrap all shared code within dedicated namespaces or Immediately Invoked Function Expressions (IIFEs) to avoid polluting the target site's execution context.
  • Version Control Dependencies: When importing external scripts via @require, link to specific release tags or commit hashes to prevent silent breaking changes from impacting your scripts.
  • Provide Graceful Fallbacks: Add conditional checks to verify that shared functions or APIs exist before executing dependent logic, displaying clear console warnings if a shared component fails to load.
