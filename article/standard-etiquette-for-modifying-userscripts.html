Standard Etiquette for Modifying Userscripts

Modifying or forking existing userscripts is a common practice in the browser customization community to fix bugs, add features, or adapt functionality for personal use. However, doing so responsibly requires adhering to established open-source etiquette. Key practices include respecting software licenses, providing clear attribution, changing script metadata to prevent technical conflicts, and attempting to contribute back to the original project before publishing a separate version.

Check the Original License

Before modifying or redistributing any code, review the original userscript’s license. Open-source licenses such as MIT, GPL, or Apache explicitly state how the code can be modified and shared. If a script has no license specified, standard copyright law applies, meaning the original author retains all rights. In cases without a license, keep your modifications private or contact the developer for permission before publishing your changes.

Attempt to Contribute First

If you notice a bug or want to add a useful feature, contact the author or submit a pull request to the original repository first. Most developers appreciate community contributions that improve the script for everyone. Creating a public fork should primarily occur when the original script is abandoned, the author declines the proposed changes, or your modifications significantly alter the script's core purpose.

Provide Proper Attribution

Always credit the original author. Include a direct link to the original script, repository, or profile within your code's header comments and on the distribution page. Acknowledging the original creator respects their effort and allows users to trace the script's history.

Update Script Metadata

To prevent technical conflicts for users who might have both versions installed, update the metadata block at the top of the userscript:

  • @name: Change the title slightly (e.g., append "Fork" or "Fixed") to differentiate it from the original.
  • @namespace: Update this to your own unique URL or identifier.
  • @downloadURL and @updateURL: Change these pointers to your own hosting site so automatic updates do not overwrite the original script or pull updates from the wrong source.

Document Your Modifications

Provide a clear summary of what you changed, added, or removed in the description or release notes of your forked script. Transparency helps users understand why your version exists and whether it suits their specific needs better than the original version.
