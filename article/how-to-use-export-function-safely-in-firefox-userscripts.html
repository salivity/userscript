How to Use exportFunction Safely in Firefox Userscripts

Firefox userscripts often need to share code or functions with a web page's DOM context without exposing privileged extension APIs to potential security exploits. The exportFunction API bridges the execution boundary between the privileged userscript environment and the unprivileged page context (unsafeWindow). This article explains how exportFunction works, the security risks associated with sharing code across security boundaries, and the practical best practices required to implement it safely in your Firefox userscripts.

Understanding the Security Boundary

Firefox isolates userscript execution from web page scripts to prevent malicious websites from hijacking powerful APIs like GM_xmlhttpRequest or GM_setValue. Directly assigning a userscript function to unsafeWindow (e.g., unsafeWindow.myFunc = myFunc) can create severe privilege escalation vulnerabilities, allowing web page scripts to execute code with userscript privileges.

The exportFunction utility safely defines a function in the privileged context and exposes a callable reference to the target untrusted window context.

Basic Usage Syntax

To expose a function safely, pass the function, the target scope (typically unsafeWindow), and an options object containing the property name:

function displayMessage(msg) {
  // Always sanitize inputs from unsafe contexts
  console.log("Page message:", String(msg));
}

exportFunction(displayMessage, unsafeWindow, { defineAs: "displayMessage" });

After execution, scripts on the web page can call window.displayMessage("Hello").

Essential Rules for Safe Implementation

1. Validate and Sanitize All Arguments

Untrusted web pages can pass tampered arguments, modified prototypes, or objects with malicious getters designed to trigger side effects inside your privileged script context.

  • Convert incoming arguments to primitive data types immediately (String(), Number(), Boolean()).
  • Avoid accessing properties on objects passed into the function by the web page.
  • Never use eval() or dynamically construct executable code from parameters.

2. Restrict Privileged API Access

Never create exported functions that act as open proxies for privileged GM/TM functions.

Vulnerable Code:

// DANGER: Allows the web page to make arbitrary privileged cross-origin requests
exportFunction(function(url) {
  GM_xmlhttpRequest({ url: url, method: "GET" });
}, unsafeWindow, { defineAs: "fetchData" });

Secure Code:

// SAFE: Strictly validates the input against an allowed list
const ALLOWED_DOMAIN = "https://api.example.com/";

exportFunction(function(endpoint) {
  const safeEndpoint = String(endpoint).replace(/[^a-zA-Z0-9]/g, "");
  const fullUrl = ALLOWED_DOMAIN + safeEndpoint;
  
  GM_xmlhttpRequest({ url: fullUrl, method: "GET" });
}, unsafeWindow, { defineAs: "fetchData" });

3. Use cloneInto When Returning Objects

If an exported function returns an object, array, or complex data structure to the web page, you must explicitly clone the object into the target scope using cloneInto. Failing to do so will result in security errors or unexpected object references across contexts.

function getUserData() {
  const payload = { status: "active", id: 101 };
  // Clone object into the unprivileged context
  return cloneInto(payload, unsafeWindow);
}

exportFunction(getUserData, unsafeWindow, { defineAs: "getUserData" });

4. Limit Global Namespace Footprint

Avoid attaching multiple functions directly to unsafeWindow. Instead, create a single custom object in the page context using cloneInto and attach your exported functions to that container object.

// Create a wrapper object in page scope
const myAppNamespace = cloneInto({}, unsafeWindow);
unsafeWindow.myApp = myAppNamespace;

// Attach exported functions to the custom namespace
exportFunction(displayMessage, myAppNamespace, { defineAs: "log" });
