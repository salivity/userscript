How Userscripts Sync State Across Browser Windows

Managing state across multiple open browser tabs or windows is a common challenge for userscript developers. Userscripts typically rely on web APIs such as the BroadcastChannel API, localStorage event listeners, or extension-specific storage APIs like GM_addValueChangeListener to keep data synchronized in real time. This article explores the primary techniques developers use to achieve seamless cross-window state synchronization, highlighting their mechanisms, pros, and ideal use cases.

1. Native Userscript Manager APIs (GM_addValueChangeListener)

The most robust method for userscripts running in environments like Tampermonkey or Violentmonkey is using the native GM_setValue and GM_addValueChangeListener APIs.

Unlike standard web APIs bound to a single domain context, GM_setValue persists data in the extension's isolated storage. When one tab updates a value using GM_setValue, the userscript manager broadcasts this change to all active instances of the script running across different windows.

How it works:

  • Writing State: Tab A calls GM_setValue('user_state', updatedData).
  • Listening for Changes: Tab B registers a listener using GM_addValueChangeListener('user_state', (name, oldValue, newValue, remote) => { ... }).
  • Cross-Origin Capability: The remote boolean flag indicates if the modification came from another tab. This method works even across different origins if the script is configured to run on multiple domains.

2. The BroadcastChannel API

For scripts operating entirely within the same domain across tabs, the native browser BroadcastChannel API provides a simple publish/subscribe communication mechanism.

How it works:

  • A channel is opened with a shared name: const channel = new BroadcastChannel('app_state');
  • Sending Data: A tab broadcasts a message using channel.postMessage(stateData).
  • Receiving Data: Other open tabs listen via channel.onmessage = (event) => updateState(event.data);.

Advantages:

  • Low latency and highly efficient.
  • Works natively without relying on persistent storage writes.
  • Supports complex JavaScript objects via the structured clone algorithm.

Limitations:

  • Restricted by the Same-Origin Policy (SOP). Tabs running on different domains cannot share a BroadcastChannel.

3. localStorage and the storage Event

Before the BroadcastChannel API became widely supported, developers used localStorage as an event bus. When a value in localStorage changes in one window, a storage event fires in every other window of the same origin.

How it works:

  • Writing State: Tab A updates storage via localStorage.setItem('state_key', JSON.stringify(newState)).
  • Listening for Changes: Tab B catches the change: 
    window.addEventListener('storage', (event) => {
  if (event.key === 'state_key') {
    const newState = JSON.parse(event.newValue);
    // Synchronize internal state
  }
});

Limitations:

  • Synchronous disk I/O operations make localStorage slower than memory-based messaging.
  • The storage event does not fire in the window that originated the change.
  • Limited to same-origin contexts.

4. SharedWorker for Complex Shared Logic

When multiple windows need not just synchronized data, but shared stateful logic (such as maintaining a single WebSocket connection across multiple tabs), a SharedWorker is used.

How it works:

  • A SharedWorker script runs in the background, independent of any single tab.
  • Every open window connects to the same worker instance via a MessagePort.
  • The worker acts as the single source of truth, managing the central state and broadcasting updates to connected ports.

Summary of Techniques

Method Cross-Origin? Real-Time? Best Used For
GM_addValueChangeListener Yes Yes General userscript state sync across any URL match
BroadcastChannel No Yes High-frequency messaging between same-domain tabs
localStorage Event No Yes (Slower) Basic fallback state sync on the same domain
