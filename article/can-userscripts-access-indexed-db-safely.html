Can Userscripts Access IndexedDB Safely?

Userscripts can safely interact with a website's IndexedDB database, provided they respect the browser's security boundaries and database transaction rules. Because userscripts execute within the target website's origin, they inherit full access to its IndexedDB instances. However, ensuring safety requires proper handling of asynchronous operations, schema versions, and execution timing to prevent data corruption or conflicts with the native application code.

How Userscripts Interact with IndexedDB

When a userscript runs via a browser extension like Tampermonkey or Violentmonkey, it operates within the context of the active webpage's origin. This means the script has direct access to the global window.indexedDB object.

Because it shares the same origin as the host site, the userscript can:

  • Open existing databases created by the website.
  • Read, insert, update, and delete records within existing object stores.
  • Listen for database events and transactions.

Potential Risks and Safety Concerns

While technical access is seamless, unsafe interaction can break site functionality or compromise data. The primary risks include:

1. Schema Conflicts

Attempting to modify the database schema (such as adding or removing object stores) requires bumping the database version number. If a userscript triggers an onupgradeneeded event unexpectedly, it can disrupt the website's own database logic, leading to broken app states or lost data.

2. Race Conditions and Execution Timing

If a userscript attempts to read or write to IndexedDB before the host website has finished initializing its own connection, it can cause locking issues or unhandled exceptions. Setting the correct @run-at directive (such as document-idle) helps ensure the site's original scripts have completed primary setup.

3. Unhandled Asynchronous Errors

IndexedDB relies heavily on event-based asynchronous requests or Promises. Failing to catch transaction aborts or request errors in a userscript can trigger global unhandled error events on the host page.

4. Data Security and Privacy

Because any script running in the same origin can access IndexedDB, installed third-party userscripts have full access to sensitive stored data, such as cached tokens or user history. Users should only install userscripts from trusted sources.

Best Practices for Safe Interaction

To safely read or modify a website's IndexedDB data through a userscript, follow these guidelines:

  • Treat the Schema as Read-Only: Avoid altering database versions or modifying object store structures unless absolutely necessary. Interacting strictly with existing stores minimizes the risk of breaking site features.
  • Respect Existing Transactions: Perform operations in short-lived, explicit transactions (readonly or readwrite). Avoid keeping transactions open longer than needed to prevent blocking the website's native background processes.
  • Wait for Page Load: Use @run-at document-idle or wait for the DOMContentLoaded event before opening a connection to ensure the site's own database initialization has finished.
  • Wrap Requests in Promises: Modernize raw IndexedDB event calls by wrapping them in Promises or using light helper functions. This makes error handling cleaner and prevents uncaught errors from propagating to the host site.
  • Intercept or Reuse Existing Connections: Where possible, inspect the site's global scripts to see if an open database connection or API wrapper is already exposed on the window object, reducing the need to open secondary connections.
