How to Handle Userscript Feature Requests

Managing feature requests from userscript users requires a balance of clear communication, realistic expectations, and open-source etiquette. This article outlines the standard guidelines for handling feature suggestions gracefully, including setting upfront scope boundaries, acknowledging user feedback, politely declining out-of-scope ideas, and encouraging community contributions.

Set Expectations with a Clear Scope

Before requests start coming in, define the purpose and boundaries of your userscript in your documentation, such as the README.md file or script description page. State clearly what the script is intended to do and what falls outside its development scope. Explicitly mention whether you are actively accepting new feature requests, only fixing bugs, or keeping the script minimal to maintain fast performance.

Acknowledge and Validate User Input

When a user submits a feature request, acknowledge their input promptly. A brief message thanking them for taking the time to share their idea goes a long way in fostering a respectful community. Even if the requested feature is not immediately actionable, letting the user know their suggestion was read prevents them from feeling ignored.

Evaluate the Request Objectively

Assess every request against three primary criteria:

  • Relevance: Does the feature align with the core objective of the userscript?
  • Feasibility: Can it be implemented without breaking existing features, degrading site performance, or causing maintenance headaches when the target website updates?
  • Demand: Would this feature benefit a significant portion of your user base, or is it a hyper-specific preference?

Decline Unwanted Features Politely

Not every request should be implemented. If a feature request does not align with your vision or adds unnecessary complexity, decline it respectfully using these steps:

  1. Thank the user: Appreciate their initiative.
  2. Give a clear reason: Explain briefly why the feature cannot be added (e.g., performance impact, maintainability concerns, or conflicting script goals).
  3. Offer alternatives: Suggest a workaround, a complementary script, or invite them to fork your script to add the feature themselves.

Example response: "Thank you for the suggestion! However, adding this feature would significantly slow down page load times for most users, which goes against the script's goal of staying lightweight. Since the project is open-source, feel free to fork the repository and implement this custom tweak for your own use."

Encourage Pull Requests

If a suggested feature is acceptable but low on your priority list, invite the user or the community to contribute. Let them know you are open to reviewing a pull request if someone wants to code the feature themselves, provided it adheres to your existing coding standards.

Keep Your Issue Tracker Organized

Organize feature requests using tag labels such as enhancement, under-consideration, help-wanted, or declined. Close issues for features you have decided not to implement to keep your issue tracker clean, but leave the thread searchable so other users do not submit duplicate requests in the future.
