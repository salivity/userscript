How Userscripts Bypass SOP with GM_xmlhttpRequest

This article explains how browser userscripts leverage the privileged GM_xmlhttpRequest API to execute cross-origin web requests. While standard web applications are strictly constrained by the browser's Same-Origin Policy (SOP), userscript managers operate with extension-level permissions that allow them to route requests around these security boundaries safely and efficiently.

Understanding the Same-Origin Policy (SOP) Constraint

The Same-Origin Policy is a fundamental security mechanism in modern web browsers. It restricts scripts running on one origin (a combination of protocol, domain, and port) from requesting or reading resources from a different origin unless the target server explicitly permits it using Cross-Origin Resource Sharing (CORS) headers.

Standard JavaScript APIs like fetch() or XMLHttpRequest strictly enforce SOP inside the web page context. If a script on example.com attempts to fetch data from api.another-domain.com without proper CORS headers, the browser blocks the response from being read by the script.

The Architecture Behind GM_xmlhttpRequest

Userscripts bypass these restrictions because they do not execute strictly within the isolated web page context. Instead, they run under the umbrella of a userscript manager extension (such as Tampermonkey, Violentmonkey, or Greasemonkey).

When a userscript calls GM_xmlhttpRequest, the request follows a specific multi-step path:

  1. API Interception: The userscript calls GM_xmlhttpRequest instead of the standard window.fetch or XMLHttpRequest.
  2. Context Bridging: The userscript manager intercepts this call and passes the request details from the web page's content script environment to the extension's background script environment via message passing.
  3. Extension-Level Execution: The background script executes the HTTP request. Because browser extensions carry elevated privileges granted by the user upon installation, requests made from an extension's background context are exempt from web-page SOP constraints.
  4. Data Delivery: Once the background script receives the HTTP response, it sanitizes and serializes the data, passing it back across the bridge to the content script's callback functions (onload, onerror, etc.).

Key Capabilities of GM_xmlhttpRequest

Because GM_xmlhttpRequest operates at the extension level, it offers several features impossible with standard front-end JavaScript:

  • Cross-Domain Data Fetching: Request data from any third-party REST API or website, regardless of whether the target server includes CORS headers (Access-Control-Allow-Origin).
  • Custom Header Manipulation: Modify restricted HTTP headers (such as User-Agent, Referer, or Cookie) that standard web scripts are forbidden from altering.
  • Cookie Management: Send and receive cookies across different domains without strict site attribute restrictions, depending on the userscript manager's granted permissions.
  • Bypassing Mixed Content Restrictions: In certain configurations, make requests across HTTP and HTTPS boundaries that would normally be blocked by browser mixed-content policies.

Security Considerations

While GM_xmlhttpRequest is a powerful tool for developers creating custom web enhancements, it also shifts security responsibilities to the user. Browsers grant extensions broad network access, meaning a malicious or compromised userscript using GM_xmlhttpRequest could potentially exfiltrate sensitive data from the current page to an unauthorized external server.

For this reason, modern userscript managers require scripts to explicitly declare permission to use the API via the @grant GM_xmlhttpRequest directive in the script header, and often require @connect rules to whitelist specific domains the script is allowed to reach.
