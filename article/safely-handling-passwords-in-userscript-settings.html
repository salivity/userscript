Safely Handling Passwords in Userscript Settings

Userscripts that interact with authenticated APIs or external services often require user credentials, making secure credential management essential. Handling passwords within custom userscript settings menus requires leveraging isolated extension storage, building sandboxed user interface elements, preventing memory leaks, and mitigating host-page Cross-Site Scripting (XSS) risks. By strictly separating the script's execution context from the host webpage, developers can safely collect and store sensitive user input without exposing it to malicious third-party scripts.

Isolated Storage Over Web Storage

The most critical step in handling sensitive credentials is choosing the correct storage mechanism. Userscripts must never store passwords or access tokens in standard web storage options like localStorage or sessionStorage. Data in web storage is bound to the page's origin, making it directly accessible to any JavaScript running on the host site, including third-party analytics, ads, or compromised scripts.

Instead, userscripts should use cross-domain extension APIs provided by managers like Tampermonkey, Violentmonkey, or Greasemonkey:

  • GM_setValue / GM.setValue: Stores data in an isolated database managed exclusively by the browser extension. The host webpage has no access to this storage.
  • GM_config: A popular library for building settings menus that should be explicitly configured to store its state using GM_setValue rather than native web storage.

UI Sandboxing and Input Protection

Creating a settings menu inside the host page's Document Object Model (DOM) can expose input fields to event listeners running on the main site. Host scripts can potentially attach global keyloggers or inspect DOM elements to capture passwords as the user types.

To mitigate input capture in custom settings UI:

  1. Use Shadow DOM or Iframes: Encapsulate the settings menu within a closed ShadowRoot or an isolated iframe. This prevents the host page from easily querying the input fields or capturing bubbling keyboard events.
  2. Disable Autocomplete: Always set autocomplete="new-password" or autocomplete="off" on password input elements to prevent the browser from saving or auto-filling credentials into the script’s custom interface.
  3. Use Proper Input Types: Always use <input type="password"> to prevent visual exposure and local shoulder surfing.

Minimizing In-Memory Exposure

Handling sensitive data in memory requires careful lifecycle management to prevent credentials from persisting longer than necessary.

  • Clear Variables Immediately: Once a password is read from the input field and passed to GM_setValue, set the local JavaScript variables holding the plaintext password to null or undefined.
  • Avoid Logging: Ensure no debug code uses console.log(), console.dir(), or custom reporting functions that might accidentally print credentials to the browser console.
  • Prefer API Tokens: Whenever possible, prompt the user for a limited-scope API key or Personal Access Token (PAT) rather than their main account password. Tokens can be easily revoked without compromising the primary account.

Defense Against Cross-Site Scripting (XSS)

Because userscripts run on top of third-party websites, an existing XSS vulnerability on the host page could compromise the execution environment if the script context is exposed.

  • Strict Content Security Policies: Grant minimum required @grant permissions in the userscript header. Avoid using @grant none, as this runs the userscript directly in the page's context (unsafeWindow), completely bypassing the safety features of GM_setValue.
  • Safe DOM Injection: When dynamically creating settings elements, avoid using innerHTML with raw user data. Use safe methods like document.createElement() and assign values using textContent to avoid injecting executable code.
