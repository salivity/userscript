How Userscripts Inject CSP Nonces for Code Execution

Content Security Policy (CSP) nonces are dynamic cryptographic tokens designed to prevent unauthorized inline script execution on modern websites. Userscripts, managed by browser extensions like Tampermonkey or Violentmonkey, frequently need to run code within the context of a page enforced by strict CSP rules. This article explains how userscript engines extract existing CSP nonces from the Document Object Model (DOM), modify HTTP headers using browser APIs, and leverage privileged extension contexts to bypass or satisfy CSP restrictions.

What Is a Content Security Policy Nonce?

A CSP nonce ("number used once") is a random string generated by the web server for every HTTP request. The server includes this string in its Content-Security-Policy header:

Content-Security-Policy: script-src 'nonce-rAnd0m12345'

For an inline script tag to execute, it must contain a matching nonce attribute:

<script nonce="rAnd0m12345">
  // Authorized code runs here
</script>

If a script lacks the correct nonce, the browser blocks its execution to defend against Cross-Site Scripting (XSS) attacks.

How Userscripts Extract and Reuse CSP Nonces

Userscript managers operate inside a privileged content script environment, giving them direct access to the webpage's DOM. To inject custom scripts into the page context (the window object of the website), userscript engines search for valid nonces already present on the page.

1. Scraping the DOM for Active Nonces

When a web page loads, legitimate inline scripts or <meta> tags often hold valid nonces. A userscript engine scans the document before running its payload:

// Query the DOM for any script element containing a nonce property
const existingScript = document.querySelector('script[nonce]');
const nonce = existingScript ? existingScript.nonce || existingScript.getAttribute('nonce') : null;

Browsers hide the nonce attribute from getAttribute() in modern specs to prevent basic XSS exfiltration, but the HTMLScriptElement.nonce IDL property remains accessible to DOM scripts.

2. Attaching the Nonce to Injected Scripts

Once the userscript manager extracts a valid nonce string, it applies that nonce to the newly created elements before injecting them into the target document:

const scriptTag = document.createElement('script');
scriptTag.textContent = `console.log("Injected code running in page context");`;

if (nonce) {
  scriptTag.setAttribute('nonce', nonce);
  // Or explicitly set the property
  scriptTag.nonce = nonce;
}

(document.head || document.documentElement).appendChild(scriptTag);

Because the injected script tag presents a nonce that matches the server's policy header, the browser's security engine treats it as trusted inline code and executes it.

Modifying HTTP CSP Headers via Extension APIs

Scraping nonces from DOM nodes is not always reliable, especially if the target website uses strict CSP rules without inline script tags. To overcome this, modern userscript managers modify the network response headers directly using browser web extension APIs.

Removing or Modifying CSP Directives

Extensions utilize APIs like chrome.webRequest (Manifest V2) or chrome.declarativeNetRequest (Manifest V3) to intercept HTTP responses before the browser parses them.

The extension can modify the header in several ways:

  • Stripping the Header: Removing the Content-Security-Policy header entirely for targeted domain requests.
  • Injecting a Known Nonce: Appending a custom nonce (e.g., 'nonce-userscript-allowed') to the header's script-src directive and attaching that same nonce to injected script elements.
  • Relaxing Restrictions: Appending 'unsafe-inline' or 'unsafe-eval' to the existing policy directives.

By altering the policy at the network layer, the userscript manager ensures that injected code runs smoothly without needing to search the DOM for original server nonces.

Modern Bypasses: Isolated Worlds and Extension APIs

In recent web extension architecture, extracting nonces is less critical than it used to be due to execution environment isolation and dedicated APIs.

Execution in the Main World

Manifest V3 extensions can execute scripts directly in the webpage's context (the "Main World") using the chrome.scripting.executeScript API with world: 'MAIN'. Scripts injected through official extension APIs operate under the extension's privileges rather than the page's standard CSP, bypassing inline nonce requirements entirely in supported browsers.

The GM_addElement Helper

Userscript engines provide built-in APIs like GM_addElement. When a script calls GM_addElement('script', { src: '...' }), the userscript manager creates and injects the element using internal extension privileges, automatically handling nonce discovery or CSP evasion behind the scenes.
