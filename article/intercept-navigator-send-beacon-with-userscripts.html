Intercept navigator.sendBeacon with Userscripts

Yes, userscripts can successfully intercept and modify or block the navigator.sendBeacon method to prevent background data tracking. By monkey-patching this native JavaScript API at page load using browser extensions like Tampermonkey or Violentmonkey, users can stop websites from transmitting analytics, telemetry, and user-behavior data when navigating away from a page.

How sendBeacon Interception Works

The navigator.sendBeacon() method is designed to asynchronously send small amounts of data over HTTP to a web server, typically when a page unloads. Because navigator.sendBeacon is a standard property of the browser's global window.navigator object, JavaScript running on the page—including userscripts—can override it.

By replacing the original navigator.sendBeacon function with a custom dummy function, a userscript can catch all incoming tracking payloads. The script can then choose to log the data, block the request entirely by returning true without calling the underlying API, or selectively filter specific tracking domains.

Step-by-Step Implementation

To effectively block sendBeacon tracking, a userscript must execute before the target website runs its own scripts. This requires setting the script execution point to document-start.

Because modern userscript managers run scripts in an isolated world, the modification must target the page's actual context (unsafeWindow or via script tag injection) rather than the extension's sandbox.

Here is a standard userscript template to block sendBeacon:

// ==UserScript==
// @name         Block sendBeacon Tracking
// @namespace    https://example.com/
// @version      1.0
// @description  Intercepts and blocks navigator.sendBeacon tracking requests.
// @match        *://*/*
// @run-at       document-start
// @grant        none
// ==UserScript==

(function() {
    'use strict';

    // Target the main window object
    const targetWindow = typeof unsafeWindow !== 'undefined' ? unsafeWindow : window;

    if (targetWindow.navigator && targetWindow.navigator.sendBeacon) {
        // Store reference to original function if logging is desired
        const originalSendBeacon = targetWindow.navigator.sendBeacon;

        // Override sendBeacon with a dummy function
        targetWindow.navigator.sendBeacon = function(url, data) {
            console.log(`[Blocked sendBeacon] URL: ${url}`, data);
            
            // Return true to simulate a successful queueing of the request
            return true;
        };
    }
})();

Technical Limitations and Considerations

While intercepting sendBeacon stops a specific tracking vector, there are important technical factors to keep in mind:

  1. Fallback Tracking Methods: If sendBeacon fails or is disabled, well-engineered tracking scripts often fall back to alternative APIs. These include fetch() with the keepalive: true flag or traditional synchronous XMLHttpRequest calls during page unload events. To fully block background tracking, those APIs may need to be intercepted as well.
  2. Website Functionality: Some non-tracking features (such as saving draft text automatically or logging essential user state) rely on sendBeacon. Outright blocking may break specific application features on complex web apps.
  3. Execution Timing: If the userscript executes after the website's initial scripts have loaded, the tracking library may have already stored a reference to the native sendBeacon function, bypassing any subsequent overrides. Setting @run-at document-start is critical.
