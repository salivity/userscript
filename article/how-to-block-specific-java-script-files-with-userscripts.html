How to Block Specific JavaScript Files with Userscripts

Yes, userscripts can prevent specific JavaScript files from loading or executing on a webpage, though success depends on execution timing and how the script is inserted into the document. By running a userscript at the earliest possible stage (@run-at document-start), developers can intercept <script> elements before they fetch or execute remote code using techniques like DOM monkey-patching, MutationObserver, or extension-specific APIs like GM_webRequest.

Why Execution Timing Matters

For a userscript to block an external JavaScript file, it must execute before the browser parses and requests that file. Standard userscripts often run at document-idle or document-end, which is too late to stop network requests for synchronous <script> tags located in the page header.

To ensure your script runs early enough, include this directive in your userscript metadata block:

// ==UserScript==
// @name         Script Blocker
// @match        https://example.com/*
// @run-at       document-start
// ==UserScript==

Method 1: Intercepting Script Creation (DOM Patching)

If the target website dynamically injects script tags via JavaScript, you can override document.createElement to prevent specific scripts from setting matching src attributes.

const originalCreateElement = document.createElement;

document.createElement = function (tagName, options) {
    const element = originalCreateElement.call(document, tagName, options);
    if (tagName.toLowerCase() === 'script') {
        Object.defineProperty(element, 'src', {
            set(url) {
                if (url.includes('unwanted-script.js')) {
                    console.log('Blocked script loading:', url);
                    return; // Stop setting the src attribute
                }
                element.setAttribute('src', url);
            },
            get() {
                return element.getAttribute('src');
            }
        });
    }
    return element;
};

Method 2: Blocking HTML-Embedded Scripts with MutationObserver

To block external scripts hardcoded directly in the original HTML source, set up a MutationObserver at document-start. This allows you to catch and modify or remove script nodes the moment they enter the DOM.

const observer = new MutationObserver((mutations) => {
    for (const mutation of mutations) {
        for (const node of mutation.addedNodes) {
            if (node.tagName === 'SCRIPT' && node.src.includes('target-script.js')) {
                // Prevent execution by changing the type attribute
                node.type = 'javascript/blocked';
                node.remove();
                console.log('Prevented execution of:', node.src);
            }
        }
    }
});

observer.observe(document.documentElement, {
    childList: true,
    subtree: true
});

Method 3: Using GM_webRequest (Network Level)

Some userscript managers (such as Violentmonkey or specific configurations of Tampermonkey) support the GM_webRequest API. This allows you to abort network requests before they reach the server level.

// ==UserScript==
// @name         Block Network Script
// @match        https://example.com/*
// @run-at       document-start
// @grant        GM_webRequest
// ==UserScript==

GM_webRequest([
    { selector: '*://example.com/path/to/script.js*', action: 'cancel' }
]);

Limitations of Using Userscripts for Script Blocking

  • Browser Pre-Parser: Modern browsers use preload scanners that might request synchronous scripts in the HTML head before userscripts complete initialization.
  • Inline Scripts: Blocking specific inline <script> blocks (scripts without a src attribute) requires removing or modifying the script element before the browser engine executes its contents, which can be difficult to catch reliably.
  • Dedicated Blockers: For strictly blocking network requests by URL pattern, dedicated content blockers (like uBlock Origin) are more reliable than userscripts because they hook directly into the browser's webRequest API at a lower system level.
