Script Tag Injection vs eval() in Userscripts

In userscripts, choosing between injecting a <script> tag and using eval() fundamentally changes how and where your code executes within the browser. Injecting a script tag appends code directly into the web page's DOM, executing it in the main page's context with access to page-level JavaScript variables but losing access to privileged userscript APIs. Conversely, eval() executes string-based code dynamically within the userscript's isolated sandbox context, retaining access to special API functions like GM_xmlhttpRequest while remaining separated from the page's global scope.

Execution Context and Scope

The primary difference between the two methods lies in the execution context:

  • Script Tag Injection: When a script creates a <script> element and appends it to the DOM (document.head.appendChild(script)), the browser interprets the code as if it originated from the website itself. The code runs inside the page's global scope (window). This allows direct manipulation of page variables, framework instances (like React or Vue internals), and global functions. However, it completely isolates the code from userscript-specific functions (such as GM_setValue or GM_getValue).
  • eval(): Executing code via eval() runs the provided string inside the current scope of the userscript engine. It maintains access to the userscript sandbox, allowing you to use privileged GM_* APIs. It cannot directly access the page's window object unless explicitly combined with unsafeWindow.

Content Security Policy (CSP) Restrictions

Websites use Content Security Policy (CSP) headers to restrict unauthorized code execution, impacting both methods differently:

  • Script Tag Injection: Strict CSP rules often block inline scripts via the script-src directive. If a site forbids inline scripts or restricts script sources, inserting a DOM script tag will fail unless the userscript manager actively overrides or bypasses the site's CSP headers.
  • eval(): Sites with a CSP that omits 'unsafe-eval' will block standard eval() execution. While modern userscript managers (like Tampermonkey or Violentmonkey) can bypass CSP restrictions within their own sandbox environments, calling eval() inside page-scoped scripts will trigger CSP errors.

Security and Isolation

Script injection exposes your custom logic to the host website. Any global variables, functions, or listeners created by an injected script tag can be detected, modified, or hijacked by the website's scripts.

Using eval() inside the userscript sandbox keeps your logic isolated from the target website. However, evaluating untrusted strings or external inputs using eval() introduces severe security risks, such as arbitrary code execution vulnerabilities within the elevated scope of the userscript.

Performance and Debugging

Code injected via DOM script tags appears directly in the browser developer tools under the page source context, making DOM breakpoints and standard debugging straightforward.

Code evaluated via eval() can be harder to debug because it is parsed at runtime as a string, often resulting in anonymous execution stacks unless explicit //# sourceURL directives are included. Additionally, JavaScript engines optimize static DOM scripts better than dynamically evaluated strings passed through eval().

Summary of Differences

  • Script Injection: Runs in the page context, accesses page global variables, cannot use GM_* APIs, subject to page DOM CSP.
  • eval(): Runs in the sandbox context, retains access to GM_* APIs, isolated from page variables, subject to strict unsafe-eval CSP unless handled by the extension sandbox.
