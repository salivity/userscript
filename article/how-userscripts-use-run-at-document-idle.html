How Userscripts Use @run-at document-idle

The @run-at document-idle directive optimizes page loading by deferring the execution of a userscript until after the main web page DOM is fully parsed and critical initial resources have finished loading. By prioritizing the website's native loading and rendering pipeline, this directive prevents user-written code from competing for CPU cycles and network bandwidth during critical startup phases, resulting in faster perceived load times and improved browser responsiveness.

Mechanism of @run-at document-idle

When browser extension engines (like Tampermonkey or Violentmonkey) process userscripts, the @run-at metadata key dictates the exact phase of the page lifecycle in which the script injects.

Setting this directive to document-idle instructs the script manager to monitor page events. The script executes after the DOMContentLoaded event fires, or after a brief fallback delay if the event has already passed or takes too long. In practice, execution occurs when the main thread experiences a pause in initial setup activity, ensuring that native site scripts execute first.

Performance Advantages

1. Unblocking the Critical Rendering Path

Browsers render web pages by parsing HTML, constructing the DOM, and applying styles. If a script executes early (using @run-at document-start or @run-at document-end), heavy computations or layout measurements can block the main thread. Deferring execution to document-idle ensures that initial paint operations occur without interruption.

2. Reducing Network Congestion

Userscripts often issue API calls via GM_xmlhttpRequest or fetch to retrieve third-party data or site enhancements. Executing these requests while the browser is downloading core JavaScript bundles, CSS stylesheets, or key images can lead to network contention. Delaying the script ensures that primary assets download at maximum bandwidth before background requests begin.

3. Avoiding Layout Thrashing

Modifying elements on a page before or during the initial rendering phase can trigger expensive dynamic reflows and repaints. By waiting until the document reaches an idle state, element dimensions and positions are finalized. Any DOM manipulation performed by the userscript at this stage executes smoothly without breaking native layout calculations.

4. Eliminating Element Race Conditions

Running scripts prematurely often requires developers to implement custom polling loops or MutationObserver instances to verify that target elements exist before manipulating them. With document-idle, target elements are generally fully loaded and accessible in the DOM, reducing script complexity and eliminating redundant execution loops.

Example Metadata Configuration

To apply this optimization, include the directive in the userscript's metadata header block:

// ==UserScript==
// @name         Optimized UI Modifier
// @namespace    http://example.com/
// @version      1.0
// @match        https://example.com/*
// @run-at       document-idle
// @grant        none
// ==UserScript==

(function() {
    'use main';
    // Script logic executes safely after the page becomes responsive
    const sidebar = document.querySelector('.sidebar');
    if (sidebar) {
        sidebar.style.backgroundColor = '#f0f0f0';
    }
})();

Best Practice Guidance

Use @run-at document-idle for any userscript tasks that do not alter the page's core functionality or layout prior to the initial visual render. Ideal use cases include UI restyling, analytics collection, third-party data integration, and automated actions on interactive elements. Reserve early execution directives like document-start exclusively for scenarios where preventing visual flickers or intercepting initial network calls is essential.
