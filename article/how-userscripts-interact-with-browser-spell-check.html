How Userscripts Interact With Browser Spell Check

Userscripts interact with a browser's native spell-checking features primarily through Document Object Model (DOM) manipulation, event handling, and HTML attribute management. While web browsers do not expose a direct JavaScript API to invoke or query the native spell-checker, userscripts can enable, disable, or modify spell-checking behavior by altering webpage elements. This article explains how userscripts interface with native spell-check settings, overcome editor limitations, and manage text modifications.

Controlling the Native Spellcheck Attribute

Browsers determine whether to spell-check an input element based on the standard HTML spellcheck attribute. Userscripts can target form fields, textareas, and editable regions to toggle this feature programmatically.

  • Enabling Spell-Check: A userscript can select input fields where spell-checking is disabled by default and set element.spellcheck = true or element.setAttribute('spellcheck', 'true').
  • Disabling Spell-Check: For code editors, custom fields, or input forms where red squiggly lines are undesirable, userscripts can set element.spellcheck = false.

When a userscript modifies this attribute, the browser's rendering engine immediately updates its behavior for that specific DOM node.

Interacting with Rich Text Editors and Frameworks

Modern web applications often replace standard <textarea> elements with custom rich text editors (such as CodeMirror, Monaco, or Draft.js) or contenteditable <div> elements.

  • contenteditable Elements: Browsers natively support spell-checking on elements with the contenteditable="true" attribute. Userscripts can inspect these elements and enforce spell-checking rules just as they would with standard form inputs.
  • Custom Frameworks: Complex editors often disable native spell-checking by default to prevent visual conflicts with custom syntax highlighting or inline decorations. A userscript can force spellcheck="true" onto the underlying editable container, though this may occasionally result in overlapping visual cues between the browser's red underline and the editor's custom styling.

Modifying Text and Triggering Re-evaluation

When a userscript automatically modifies, replaces, or auto-corrects text within an input field, it alters the underlying DOM node.

  1. DOM Mutation: The userscript updates the value property of an input/textarea or the textContent/innerHTML of a contenteditable element.
  2. Native Re-checking: Once the text change occurs, the browser's background spell-check thread automatically re-evaluates the newly inserted text.
  3. Event Dispatching: To ensure both the browser spell-checker and the website's internal scripts recognize the change, userscripts often dispatch synthetic input or change events: 
    element.value = "Updated text";
element.dispatchEvent(new Event('input', { bubbles: true }));

Browser Isolation and API Limitations

Userscripts run in an isolated JavaScript context (often referred to as an "Isolated World"). This design introduces specific technical boundaries regarding native spell-checking:

  • No Direct Access to Dictionary Data: Userscripts cannot read the browser's custom user dictionary, check individual words against the native dictionary programmatically, or add words to the native dictionary via JavaScript.
  • No Access to Native UI Context Menus: The native context menu options (such as "Add to dictionary" or native spelling suggestions) are handled entirely by the browser operating system layer. Userscripts cannot directly manipulate these native context menu items unless they create a completely custom, overlay-based context menu in the DOM.

To implement custom spell-checking features—such as integrated medical dictionaries or multi-language checking—userscripts typically bypass the browser's native engine entirely by fetching suggestions from external APIs or embedding lightweight third-party spell-checking libraries.
