How Userscripts Manage State During SPA Navigation

Single Page Applications (SPAs) navigate between pages by dynamically updating the DOM via client-side routing rather than triggering full browser reloads. Because the page never unloads, userscripts remain active in memory throughout the browsing session. To manage state effectively during SPA transitions, userscripts must detect client-side route changes, maintain in-memory or persistent data models, and clean up or re-initialize DOM modifications when the active view shifts.

Why SPA Navigation Retains Userscript State

In traditional Multi-Page Applications (MPAs), every link click unloads the document, wiping the JavaScript execution environment and resetting all userscript variables. In an SPA, client-side routers (such as React Router, Vue Router, or Next.js) intercept click events and update the URL using the HTML5 History API (pushState and replaceState) without reloading the document.

Because the underlying window context persists:

  • Global variables, closures, and data structures inside the userscript remain intact across route changes.
  • Event listeners attached to persistent elements remain active.
  • Injected styles and persistent DOM nodes stay rendered unless manually removed.

Detecting Client-Side Route Changes

Standard userscript entry triggers like @run-at document-end or native DOMContentLoaded events only fire on the initial page load. To react to subsequent SPA route changes, userscripts must implement dynamic URL and DOM tracking mechanisms.

1. Intercepting the History API

Standard browsers do not fire a native event when history.pushState() or history.replaceState() is called programmatically by a router. Userscripts bypass this limitation by monkey-patching these methods to dispatch custom events:

const fireRouteChange = () => window.dispatchEvent(new Event('locationchange'));

const originalPushState = history.pushState;
history.pushState = function (...args) {
  originalPushState.apply(this, args);
  fireRouteChange();
};

const originalReplaceState = history.replaceState;
history.replaceState = function (...args) {
  originalReplaceState.apply(this, args);
  fireRouteChange();
};

window.addEventListener('popstate', fireRouteChange);
window.addEventListener('locationchange', () => {
  console.log('Route changed to:', location.href);
  // Re-run state management and UI injection logic
});

2. Using MutationObserver for Target Containers

If a framework bypasses standard history calls or uses heavy dynamic rendering, userscripts observe changes in the primary application container (e.g., #app or <main>) or watch for changes to the <title> tag:

const observer = new MutationObserver(() => {
  if (this.lastPath !== location.pathname) {
    this.lastPath = location.pathname;
    onUrlChange();
  }
});

observer.observe(document.querySelector('head title'), { childList: true });

Strategies for Managing State

Userscript developers use a combination of short-term in-memory state and long-term persistent storage to keep data accurate as the user navigates an SPA.

In-Memory State Caching

Because the global scope persists, userscripts can store application state in simple JavaScript objects or maps. This is ideal for caching API responses, tracking UI states, or holding component reference counts while navigating between tabs within the same session.

Persistent Storage APIs

For state that must survive hard refreshes, tab closures, or cross-origin transitions, userscripts leverage userscript manager storage functions rather than standard localStorage:

  • GM_setValue(key, value) / GM_getValue(key): Stores data asynchronously (or synchronously depending on the manager) in an isolated storage space unattached to the site’s client-side storage, preventing site scripts from altering or detecting userscript data.
  • IndexedDB: Used for storing large amounts of structured state or local databases that must persist across sessions.

Resetting and Re-synchronizing UI State

When navigating an SPA, injecting duplicate elements or attaching duplicate listeners to dynamic routes is a common issue. Effective state management requires a clear tear-down and setup lifecycle:

  1. Cleanup Phase: Upon detecting a route change, the script removes obsolete DOM elements, detaches dangling event listeners, and cancels active fetch requests or timers.
  2. State Re-evaluation: The script reads the new URL parameters or path, pulls relevant data from the local state cache or persistent storage, and determines if modification is required for the new view.
  3. DOM Re-injection: The script waits for the SPA framework to mount the new route's target elements (often via window.requestAnimationFrame or MutationObserver) before rendering updated UI elements using the recalculated state.
