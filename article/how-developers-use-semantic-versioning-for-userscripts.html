How Developers Use Semantic Versioning for Userscripts

Semantic versioning (SemVer) allows userscript developers to systematically track changes, manage user expectations, and ensure smooth automated updates through userscript managers like Tampermonkey or Violentmonkey. By adopting the standard MAJOR.MINOR.PATCH format within the metadata block of a script, developers can clearly communicate whether an update introduces breaking changes, new functionality, or minor bug fixes. This article explains how developers configure script metadata, apply SemVer rules to web-based extensions, and best practices for managing script releases.

The Userscript Metadata Header

Userscript managers rely on the script's metadata block to detect updates. Developers define the version using the @version key at the top of the JavaScript file.

// ==UserScript==
// @name         Example Enhancement Script
// @namespace    http://tampermonkey.net/
// @version      1.2.4
// @description  Adds custom features to targeted websites.
// ==UserScript==

When a script is hosted on a repository or script hub (such as Greasy Fork or GitHub), userscript managers periodically check the @version string. If the remote version number is higher than the installed version, the manager prompts or automatically executes the update.

Applying SemVer Structure (MAJOR.MINOR.PATCH)

Developers structure the three-digit version number based on the nature of the changes made to the code:

1. MAJOR Version (X.0.0)

Developers increment the MAJOR version when making incompatible API changes or structural overhauls that could break existing user configurations.

  • Examples:
    • Complete UI rewrites that remove previously available features.
    • Structural changes to stored user settings (e.g., altering GM_getValue data structures without backward compatibility).
    • Major shifts in script scope, requiring completely new @grant permissions.

2. MINOR Version (1.X.0)

Developers increment the MINOR version when adding functionality in a backward-compatible manner.

  • Examples:
    • Adding a new feature or setting toggle to the script's configuration menu.
    • Expanding support to a new domain via @match or @include.
    • Adding keyboard shortcuts while preserving existing functionality.

3. PATCH Version (1.0.X)

Developers increment the PATCH version for backward-compatible bug fixes and maintenance updates. In userscript development, patch updates occur frequently due to external changes on target websites.

  • Examples:
    • Updating DOM selectors after a target website changes its class names or HTML structure.
    • Fixing visual bugs or layout misalignments.
    • Resolving performance bottlenecks or memory leaks.

Pre-releases and Build Metadata

For testing experimental features, developers use SemVer pre-release tags, such as 2.0.0-alpha.1 or 1.1.0-beta.2. While standard SemVer supports these tags, developers must ensure their targeted userscript manager supports pre-release string parsing, as some simple update checkers only parse strict numerical values.

Key Best Practices

  • Always Increment Sequentially: Userscript updates only trigger if the new version string evaluates as greater than the old one. Developers avoid skipping logical version increments.
  • Maintain Backward Compatibility for Storage: When modifying local storage keys (GM_setValue), developers write migration functions during MINOR and PATCH updates to ensure user preferences are not lost.
  • Document Changes: Developers pair version increments with detailed changelogs on code repositories or script hosting platforms so users understand what changed in each release.
