What is the @inject-into Userscript Directive?

The @inject-into directive is a metadata tag used by modern userscript managers such as Violentmonkey and Tampermonkey to define the execution context of a script. It dictates whether a userscript runs directly within the web page's global scope, in an isolated extension environment, or in an automatically chosen context based on requested permissions. This article explains the @inject-into directive, details its three primary modes—page, content, and auto—and demonstrates how it controls script capabilities, access to page variables, and security boundaries.

Understanding Userscript Execution Contexts

Browser userscript managers must balance script security with functional access to web pages. Traditionally, userscripts ran in an isolated environment to prevent malicious web pages from accessing powerful extension APIs (such as cross-origin HTTP requests). However, userscripts often need direct access to global JavaScript objects created by the target website. The @inject-into directive allows developers to explicitly choose the environment in which their script executes.

The Three @inject-into Modes

The @inject-into directive accepts three primary values:

1. page

Setting @inject-into page injects the script directly into the context of the target web page (often referred to as the main world).

  • Behavior: The script shares the exact same window object and global variables as the web page's own JavaScript code.
  • Advantages: Allows direct manipulation of global variables, functions, and frontend framework instances (such as React or Vue components) defined by the website.
  • Limitations: The script generally loses access to privileged GM_* APIs (such as GM_xmlhttpRequest) to prevent the host site from hijacking these elevated capabilities.

2. content

Setting @inject-into content runs the script in an isolated context, similar to standard browser extension content scripts.

  • Behavior: The script operates in an isolated environment with access to the page's DOM, but it maintains a separate window object from the web page.
  • Advantages: Protects the userscript from page-level scripts, prevents variable collisions, and allows safe access to privileged GM_* functions.
  • Limitations: The script cannot directly read or modify JavaScript variables or functions attached to the web page's global window object without using explicit window messaging.

3. auto

Setting @inject-into auto (or omitting the directive) delegates the injection decision to the userscript manager.

  • Behavior: The script manager inspects the script's @grant rules. If privileged GM_* APIs are requested, the manager defaults to the content context for security. If no elevated APIs are requested, it may inject into the page context for performance and compatibility.

How @inject-into Controls Script Execution

The @inject-into directive alters the environment in three key ways:

  • Scope and Variable Visibility: page mode enables direct interaction with site-defined scripts, while content mode isolates script state from site scripts.
  • API Permission Enforcement: Privileged APIs declared in @grant headers remain active in content mode but are restricted or disabled in page mode to enforce security boundaries.
  • Handling Content Security Policy (CSP): Some modern websites use strict CSP headers that restrict dynamically added script tags. Selecting the appropriate @inject-into context helps the userscript manager determine the best mechanism to run the code without triggering browser CSP violations.
