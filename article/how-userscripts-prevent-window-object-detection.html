How Userscripts Prevent Window Object Detection

Userscripts allow browser extensions to modify web pages, but site scripts often attempt to detect their presence by searching the global window object for unexpected properties or overridden functions. To prevent detection, userscript managers and developers use techniques like isolated execution contexts, lexical scoping, secure API storage, and cleanup mechanisms. This guide explains the primary methods userscripts use to remain invisible to website scripts inspecting the window object.

1. Isolated Execution Contexts (Content Scripts)

Modern userscript managers (such as Tampermonkey, Violentmonkey, and Greasemonkey) execute scripts in a separate execution environment often referred to as an "isolated context" or sandbox.

  • Separate window Objects: The browser provides two different window objects: one for the page's original scripts and one for the userscript extension.
  • Invisible Global Variables: If a userscript assigns a variable to its global context (e.g., window.myPlugin = true), that property only exists inside the extension's isolated environment. The web page’s own scripts inspecting window.myPlugin will receive undefined.

2. Using Closures and IIFEs

When userscripts run in the main page context (such as when using @grant none or direct script injection), they avoid attaching variables directly to the global object by encapsulating their code within an Immediately Invoked Function Expression (IIFE) or block scope.

(function() {
    // Variables declared here are scoped to this function
    const privateData = "hidden";
    
    // Website scripts checking window.privateData cannot see this
})();

By keeping variables within local lexical scopes using const, let, or function closures, no trace of the script's internal state leaks to window.

3. Storage via Userscript APIs Instead of window

To persist data across page loads or share state between scripts, developers avoid using global JavaScript objects or window.localStorage. Instead, they grant scripts access to dedicated extension APIs using metadata blocks.

  • Using directives like @grant GM_setValue and @grant GM_getValue stores data inside the extension's isolated browser storage.
  • Because this storage operates outside the document object model (DOM) and page context, web page scripts cannot inspect or access it.

4. Avoiding Native Prototype Pollution and Global Overrides

Websites often check if standard window methods (like fetch, XMLHttpRequest, or console.log) have been modified by checking their .toString() output or object references.

When userscripts must modify standard window APIs, they conceal changes by:

  • Restoring toString() behavior: Custom functions can override Function.prototype.toString to return "function fetch() { [native code] }" when inspected.
  • Using Object Redefinition: Using Object.defineProperty with specific descriptors (configurable: false, enumerable: false) prevents sites from easily iterating over window keys to discover added properties.

5. Careful Use of unsafeWindow

In scenarios where a script must interact with the page's actual global scope, userscript engines provide access through unsafeWindow.

To avoid detection while using unsafeWindow:

  • Scripts read properties from unsafeWindow without writing new properties back to it.
  • Temporary properties attached to unsafeWindow for communication are immediately deleted using the delete operator after execution.
  • Clone utilities like cloneInto() or exportFunction() (in Firefox environments) are used to safely pass data without leaving prototype footprints.
