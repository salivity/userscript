How Developers Mock Browser Environments for Userscripts

Testing userscripts requires simulating both standard browser APIs and specialized user manager APIs like GM_getValue or GM_xmlhttpRequest. Developers isolate and unit test userscripts by combining headless DOM implementations such as jsdom or Happy DOM, creating custom stubs for Greasemonkey and Tampermonkey functions, and executing tests inside modern runners like Jest or Vitest. This guide explores the primary tools and techniques developers use to build lightweight, reliable mock environments for userscript development.

1. Simulating the DOM with Virtual Environments

Userscripts interact heavily with the Document Object Model (DOM). Since Node.js lacks a native DOM, developers use lightweight virtual browser environments to execute DOM manipulations without launching an actual browser.

  • jsdom: The most widely used JavaScript implementation of web standards for Node.js. It recreates the window, document, and HTML element APIs.
  • Happy DOM: A faster, lighter alternative to jsdom often paired with Vitest for faster execution.

In a test setup file, developers attach these virtual instances to the global Node.js scope:

import { JSDOM } from 'jsdom';

const dom = new JSDOM('<!querySelectorAll("html")><html><body><div id="app"></div></body></html>', {
  url: 'https://example.com/',
});

global.window = dom.window;
global.document = dom.window.document;
global.HTMLElement = dom.window.HTMLElement;

2. Mocking GM_* and User Script Manager APIs

Userscripts rely on privileged functions provided by extension managers like Tampermonkey, Violentmonkey, or Greasemonkey (e.g., GM_setValue, GM_getResourceText). Because these APIs do not exist in standard browser environments or Node.js, they must be manually mocked.

Synchronous Storage Mocks (GM_getValue / GM_setValue)

Developers frequently mock persistent storage APIs using simple JavaScript Map objects or in-memory key-value stores:

const storage = new Map();

global.GM_setValue = (key, value) => {
  storage.set(key, value);
};

global.GM_getValue = (key, defaultValue) => {
  return storage.has(key) ? storage.get(key) : defaultValue;
};

Modern Object-Based APIs (GM.*)

For scripts using the modern GM.getValue promise-based syntax, mocks are wrapped in resolved promises:

global.GM = {
  getValue: async (key, defaultValue) => storage.get(key) ?? defaultValue,
  setValue: async (key, value) => storage.set(key, value),
};

3. Mocking Network Requests (GM_xmlhttpRequest)

Standard fetch or XMLHttpRequest mocks often fail to capture GM_xmlhttpRequest behavior due to its cross-origin capabilities and specific event-driven callback structure (onload, onerror, onreadystatechange).

Developers create functional stubs using spying libraries like Sinon.js or built-in test runner functions (jest.fn() / vi.fn()):

global.GM_xmlhttpRequest = jest.fn((details) => {
  if (details.url.includes('/api/data')) {
    details.onload({
      status: 200,
      responseText: JSON.stringify({ success: true }),
    });
  } else {
    details.onerror({ status: 404 });
  }
});

4. Structuring Scripts for Testability

To make userscripts testable, developers move away from monolithic single-file scripts and adopt modular architectures using build tools like Rollup, Webpack, or Vite.

  1. Separate Logic from Metadata: The userscript header block (// ==UserScript==) is maintained separately or prepended during the build step.
  2. Export Functions via ESM: Core functions are exported as standard ES modules for unit testing and bundled into an IIFE (Immediately Invoked Function Expression) for production deployment.
  3. Dependency Injection: Functions accept APIs (like storage or network utilities) as parameters rather than referencing global variables directly, simplifying mock substitution.

5. Integrating Mocks into Test Runners

Modern frameworks like Vitest and Jest simplify environment mocking using configuration options and setup files.

Example Vitest Setup

In vitest.config.js:

export default {
  test: {
    environment: 'happy-dom',
    setupFiles: ['./test/setup-gm-mocks.js'],
  },
};

The setup-gm-mocks.js file populates the global namespace before any unit test suite runs, ensuring seamless API access across all tests.

Summary of Common Stack Configurations

  • Vitest + Happy DOM + Custom Stubs: Fast, modern setup ideal for TypeScript-based userscripts.
  • Jest + jsdom + jest.fn(): Highly stable setup suitable for complex DOM manipulation testing.
  • Playwright / Puppeteer: Used for end-to-end (E2E) integration testing in actual browser instances when unit mocks are insufficient.
