Userscript Debugging: GM_log vs console.log

In userscript development, outputting messages to trace code execution and inspect variable states is a fundamental debugging practice. While web developers traditionally rely on the standard console.log function, userscript authors can also utilize GM_log, a legacy and manager-provided API function provided by script managers like Greasemonkey, Tampermonkey, and Violentmonkey. This article breaks down how userscripts utilize GM_log compared to console.log, detailing differences in context execution, output target locations, object formatting, and permission requirements.

Overview of console.log in Userscripts

console.log is a native JavaScript method provided by the browser environment (window.console). When used inside a userscript, it outputs directly to the browser's Web Developer Tools console for the active page.

  • No Grants Required: It works immediately without requiring special permissions in the userscript metadata block (// ==UserScript==).
  • Rich Object Inspection: It supports native JavaScript object expansion, table formatting (console.table), styling via CSS, and dynamic variable references.
  • Context Awareness: In userscript managers operating with sandboxed contexts (such as @grant GM_getValue), console.log outputs from within that sandbox context, which can usually be selected via the dev tools context dropdown menu.

Overview of GM_log in Userscripts

GM_log is a dedicated API function historically created for Greasemonkey to send messages from a userscript to the browser’s extension error console or background process, rather than the web page's standard developer log.

  • Requires @grant Header: To use GM_log, the userscript header must explicitly declare @grant GM_log.
  • Isolated Log Channel: In older implementations and specific environments, GM_log writes to the script manager's background log or extension console rather than the web page's console, helping to separate userscript output from the target website's own logs.
  • Metadata Attachment: Modern script managers often format GM_log output by automatically prefixing the script’s name or version to the log output, making it easier to filter logs when running multiple scripts.

Key Differences for Debugging

1. Security Context and Overriding

Target websites can easily override or block the native console.log method (e.g., window.console.log = function() {}) to prevent users or scripts from logging data to the web console. Because GM_log operates through the privileged background API of the extension manager, it bypasses web page attempts to overwrite logging behavior.

2. Log Destination and Visibility

  • console.log: Displays directly in the main browser console alongside all network errors, site warnings, and web application scripts.
  • GM_log: Depending on the browser and userscript manager used, logs may appear in the extension’s background page context, a specialized manager logging tab, or directly in the main console with automated prefixes identifying the userscript.

3. Data Types and String Conversion

  • console.log: Passes objects by reference, allowing interactive inspection of nested structures, arrays, and DOM elements in real-time.
  • GM_log: Historically converts non-string parameters into string representations (often resulting in [object Object]). While modern script managers have improved object handling for GM_log, it remains less feature-rich for complex object inspection compared to native console methods.

4. Code Portability and Standards

  • console.log: Standard across all JavaScript environments, including web pages, Node.js, and browser extensions.
  • GM_log: Non-standard API exclusive to userscript environments. Scripts relying heavily on GM_log cannot run natively as web page scripts without polyfills.

Practical Recommendations

  • Use console.log as the default choice for active development, rich object inspection, and when standard console styling or grouping features are needed.
  • Use GM_log when writing scripts for environments where web pages actively alter or disable console.log, or when maintaining legacy scripts that require isolated extension-level log tracking.
