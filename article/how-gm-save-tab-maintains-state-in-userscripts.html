How GM_saveTab Maintains State in Userscripts

The GM_saveTab function is a specialized userscript API provided by browser extensions like Tampermonkey and Violentmonkey that allows developers to persist custom data bound specifically to an individual browser tab. Unlike global storage methods, GM_saveTab preserves an object's state across page reloads and navigations within that single tab, clearing the data automatically once the tab is closed. This article explains what GM_saveTab is, how it functions under the hood, how it compares to alternative storage options, and how to implement it effectively in your code.

What is GM_saveTab?

GM_saveTab is an asynchronous API function used to store a JavaScript object containing key-value pairs tied directly to the browser tab executing the script.

To use it alongside its counterpart GM_getTab, you must request permissions in your userscript's metadata block:

// ==UserScript==
// @name         Tab State Manager
// @match        https://example.com/*
// @grant        GM_saveTab
// @grant        GM_getTab
// ==UserScript==

How GM_saveTab Maintains State Across Reloads

Userscript managers assign an internal unique identifier to every open browser tab. When you call GM_saveTab, the manager attaches the data object you pass to that specific tab's internal ID.

Here is the mechanics of how state is maintained:

  1. Tab ID Mapping: The data is stored in the extension's background memory space, mapped to the browser tab ID rather than the web page origin.
  2. Page Navigation & Reloads: When the page reloads or navigates to a new URL where the script is active, the tab ID remains identical.
  3. State Retrieval: The script executes GM_getTab() upon loading, fetching the previously saved data object associated with that tab ID.
  4. Lifecycle Termination: Once the user closes the tab, the extension releases the saved object from memory.

Comparing GM_saveTab to Other Storage Options

Understanding when to use GM_saveTab depends on how it compares to alternative client-side storage mechanisms:

Feature GM_saveTab GM_setValue sessionStorage
Scope Single tab instance All tabs globally Single tab instance
Persistence Lives until tab closes Permanent until deleted Lives until tab closes
Cross-Domain Support Yes (moves across sites in same tab) Yes No (tied to same-origin policy)
Data Clean-up Automatic on tab close Manual required Automatic on tab close

GM_saveTab excels when you need cross-domain tracking within one tab without polluting global storage or leaking data to other open tabs running the same script.

Practical Implementation Example

To save and retrieve data across reloads, combine GM_saveTab with GM_getTab:

// Retrieve existing state or initialize defaults
GM_getTab((tab) => {
    // If state doesn't exist, create it
    if (!tab.reloadCount) {
        tab.reloadCount = 0;
    }

    // Increment counter
    tab.reloadCount += 1;
    console.log(`This tab has been reloaded ${tab.reloadCount} times.`);

    // Save updated state back to the tab
    GM_saveTab(tab);
});

Common Use Cases

  • Multi-Step Automation: Preserving step counters or form data when an automated script navigates through a multi-page sequence in one tab.
  • Tab-Isolated Configurations: Applying custom display toggles or filters that apply only to the active tab without overriding user settings in other tabs.
  • Cross-Origin Workflows: Carrying temporary variables across redirects between different domains (e.g., passing authorization tokens during a multi-site workflow).
