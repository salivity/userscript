How Userscripts Handle Layout Thrashing

Layout thrashing occurs when a userscript repeatedly reads layout properties and updates the Document Object Model (DOM) in rapid succession, forcing the browser to constantly recalculate geometry and repaint the page. When dynamically resizing multiple page elements, userscripts maintain high performance and prevent UI lag by altering how and when DOM modifications occur. By separating DOM read operations from write operations, leveraging asynchronous rendering APIs like requestAnimationFrame, and delegating layout calculations to native CSS properties, userscripts bypass forced synchronous reflows.

The Cause: Forced Synchronous Reflows

Browsers optimize layout recalculations by queuing DOM changes and executing them in batches. However, if a script reads a layout-sensitive property—such as offsetWidth, clientHeight, or getBoundingClientRect()—immediately after modifying a style property, the browser must instantly recalculate the layout to return accurate measurements. In a loop resizing dozens of elements, alternating between reading and writing triggers layout thrashing, severely degrading frame rates.

Separate Reads from Writes

The primary technique for preventing layout thrashing is batching DOM operations into distinct execution phases:

  1. Read Phase: Query all necessary element dimensions, scroll positions, or computed styles into local variables first.
  2. Write Phase: Apply all style adjustments, class toggles, or inline dimensions simultaneously after all measurements are complete.

By ensuring no geometric properties are queried during the write phase, the browser performs a single layout calculation for all updated elements.

Utilizing requestAnimationFrame

To synchronize updates with the browser's native rendering pipeline, userscripts wrap DOM write operations in requestAnimationFrame(). This defers visual updates until just before the next repaint, ensuring that script execution does not interrupt ongoing layout passes.

When handling high-frequency events, such as window resizing or mouse dragging, userscripts throttle updates by combining requestAnimationFrame() with a execution flag to ensure only one DOM write operation is queued per frame:

let scheduled = false;

function resizeElements(elements) {
  if (scheduled) return;
  scheduled = true;

  requestAnimationFrame(() => {
    // Perform batched DOM writes here
    elements.forEach(el => el.style.width = '200px');
    scheduled = false;
  });
}

Delegating Adjustments to CSS

Directly modifying inline styles on multiple individual DOM nodes via JavaScript is expensive. Efficient userscripts reduce layout work by offloading sizing logic to CSS:

  • CSS Custom Properties: The script updates a single CSS variable on a parent container or document.documentElement, allowing the browser's native CSS engine to resize all target child elements simultaneously.
  • Class Toggling: Instead of calculating and setting widths on every element inside a JavaScript loop, userscripts toggle a single utility class on a common ancestor node.
  • Hardware-Accelerated Transforms: Where applicable, userscripts use transform: scale() instead of altering explicit width or height properties. Transforms operate on the compositor thread and bypass the layout phase entirely.

Detached DOM Nodes and Document Fragments

When creating or heavily modifying multiple elements dynamically, userscripts perform calculations and structural alterations on detached nodes or inside a DocumentFragment. Because these elements are not attached to the active DOM tree, measuring and altering them offscreen incurs zero layout cost. The fully prepared elements are then appended to the live document in a single DOM manipulation.
