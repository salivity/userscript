How Userscripts Avoid CORS Errors in Fetch Requests

Userscripts can execute asynchronous network requests across different domains without running into Cross-Origin Resource Sharing (CORS) restrictions, unlike standard webpage scripts. This bypass is possible because userscript managers operate within the privileged context of browser extensions, granting them elevated permissions. By using dedicated API functions provided by the userscript engine—such as GM_xmlhttpRequest or GM.xmlHttpRequest—userscripts route requests through the browser's extension background scripts, effectively stepping outside the web page’s security sandbox.

The Web Sandbox and CORS Restrictions

Standard client-side JavaScript executing inside a browser tab is bound by the Same-Origin Policy (SOP). When a script on example.com attempts to fetch data from api.anotherdomain.com, the browser sends an asynchronous fetch or XMLHttpRequest. If the receiving server does not include the appropriate CORS headers (such as Access-Control-Allow-Origin), the browser blocks the response, throwing a CORS error to protect user data.

If a userscript relies solely on standard window.fetch() or window.XMLHttpRequest, it executes within the context of the host webpage and remains subject to these identical CORS restrictions.

How Userscript Managers Bypass CORS

Userscript managers (such as Tampermonkey, Violentmonkey, or Greasemonkey) function as browser extensions. Browser extensions hold permission models distinct from standard web pages. During installation or execution, extension manifests declare permissions—often including access to arbitrary URLs (<all_urls> or specific host patterns).

Because browser extension background processes are not bound by the Same-Origin Policy, they can make network requests to any domain without CORS enforcement.

Userscripts tap into this elevated privilege using a multi-step process:

  1. Metadata Declaration: The script declares required permissions in its metadata block using the @grant directive (e.g., @grant GM_xmlhttpRequest or @grant GM.xmlHttpRequest).
  2. Context Delegation: When the userscript calls GM_xmlhttpRequest, the request is not executed directly by the web page's browser tab. Instead, the userscript manager intercepts the call.
  3. Inter-Process Communication (IPC): The manager relays the request details (URL, method, headers, payload) to its privileged extension background context via browser extension messaging APIs.
  4. Execution and Return: The background context executes the HTTP request natively. Because it is an extension process, the browser does not enforce CORS pre-flight checks or block non-CORS response headers. Once received, the response data is sent back across the extension boundary to the userscript.

standard fetch vs. GM_xmlhttpRequest

To ensure an asynchronous request bypasses CORS errors, userscripts must explicitly use the manager's API instead of native web APIs.

  • Native fetch() / XMLHttpRequest: Bound by SOP/CORS. Subject to origin headers enforced by the host tab.
  • GM_xmlhttpRequest (or GM.xmlHttpRequest): Bypasses SOP/CORS completely. Allows setting arbitrary request headers (like custom User-Agent or Referer headers) that standard web scripts are forbidden from modifying.

Modern userscript environments also offer promise-based wrappers around these legacy APIs, enabling async/await syntax while still routing requests through the background extension layer, ensuring seamless asynchronous handling without CORS limitations.
