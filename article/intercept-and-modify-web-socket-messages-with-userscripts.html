Intercept and Modify WebSocket Messages with Userscripts

Yes, userscripts can intercept and modify WebSocket messages in real-time. Because userscripts run directly in the context of the browser page, they can override the native window.WebSocket object before the target website establishes a connection. By monkey-patching the global WebSocket constructor and its prototype methods, userscripts gain full control over both outgoing and incoming network frames.

How Userscript WebSocket Interception Works

WebSockets rely on the browser's built-in WebSocket API. Since JavaScript allows global browser objects to be redefined, a userscript can replace the default WebSocket constructor with a custom wrapper function.

When the web application instantiates a new connection using new WebSocket(url), the calls pass through the userscript's wrapper instead of going directly to the browser engine.

Intercepting Outgoing Messages

To inspect or alter data sent from the client to the server, userscripts override the send method on the WebSocket.prototype.

When the web application attempts to send data, the overridden send function intercepts the payload. The script can then log the payload, alter the string or binary buffer, or block the transmission entirely before passing the modified data to the original send implementation.

Intercepting Incoming Messages

Modifying messages coming from the server to the client requires intercepting event listeners. This is typically done through two vectors:

  1. The onmessage Property Setter: The userscript replaces the setter for the onmessage property on the custom WebSocket instance. When the application assigns a handler to ws.onmessage, the script wraps that handler in a custom function that intercepts incoming event data before invoking the original callback.
  2. The addEventListener Method: The userscript overrides WebSocket.prototype.addEventListener. When the application registers a listener for the 'message' event, the wrapper captures incoming MessageEvent objects, allows modification of the .data property, and forwards the modified event to the application's original listener.

Execution Timing Requirements

For a userscript to successfully intercept WebSockets, it must execute before the target web application initializes its own connections. In browser extensions like Tampermonkey or Violentmonkey, this is achieved by adding the following metadata directive:

// ==UserScript==
// @run-at document-start
// ==UserScript==

Setting @run-at document-start ensures the global window.WebSocket constructor is patched as early as possible in the DOM lifecycle.

Handling Binary Data and Anti-Tampering

  • Data Formats: WebSockets transport data as plain text (often JSON) or binary formats (ArrayBuffer or Blob). While text/JSON payloads are easy to parse and alter, binary data requires decoding and re-encoding using utility objects like DataView, TextDecoder, or Uint8Array.
  • Encrypted Connections (WSS): Secure WebSocket connections (wss://) encrypt traffic over TLS between the browser and server. However, because interception occurs inside the browser execution context, the data is captured after TLS decryption (incoming) or before TLS encryption (outgoing).
  • Framework Protections: Some complex applications store references to the native window.WebSocket inside private closures before external scripts run, or validate object integrity using Function.prototype.toString. Advanced userscripts counter this by spoofing native function strings or injecting the monkey-patch via inline <script> tags as close to page load as possible.
