How Userscripts Access Hardware via WebHID and WebSerial

Userscripts can interact directly with local hardware devices by leveraging modern browser standards such as the WebHID and WebSerial APIs. Running inside browser extensions like Tampermonkey or Violentmonkey, these scripts access standard DOM objects—navigator.hid and navigator.serial—to establish direct communication lines with USB, Bluetooth HID, and serial peripherals. This article explains how userscripts hook into these APIs, handle strict browser security models, manage device permissions, and facilitate real-time data transfer between web pages and connected hardware.

Understanding the Browser APIs

The WebHID API enables web applications to connect with Human Interface Devices (such as gamepads, specialized keyboards, and hardware control panels), while the WebSerial API allows direct communication with serial devices like microcontrollers, Arduinos, and serial bridges. Because userscripts execute within the context of an open web page, they share the page's execution environment and have access to these hardware APIs if the underlying browser supports them (primarily Chromium-based browsers like Chrome, Edge, and Opera).

Permission Requirements and User Activation

Browsers enforce strict security controls over hardware interaction. Neither WebHID nor WebSerial allows arbitrary background access to hardware without explicit user approval.

  1. Secure Contexts: Both APIs require a secure context (https://).
  2. User Gesture Requirement: A device connection request can only be initiated by an explicit user gesture, such as a mouse click. A userscript cannot automatically trigger device selection dialogs on page load.
  3. Permission Prompts: Calling navigator.hid.requestDevice() or navigator.serial.requestPort() triggers a browser-native modal asking the user to select and authorize a specific device.

Interacting with Hardware via Userscripts

1. Injecting UI Controls

To satisfy the user gesture requirement, a userscript typically injects a button or custom control panel into the DOM of the target website.

// Example: Injecting a button to trigger hardware connection
const btn = document.createElement('button');
btn.textContent = 'Connect Hardware';
btn.onclick = async () => {
  const port = await navigator.serial.requestPort();
  await port.open({ baudRate: 9600 });
  // Device connected and open
};
document.body.appendChild(btn);

2. Communicating via WebHID

Once access to a HID device is granted, the userscript connects to the device, opens it, and listens for input reports or writes output reports:

  • Reading Data: The script attaches an event listener to the device for the inputreport event to receive data packets sent by the device.
  • Sending Data: The script uses device.sendReport() or device.sendFeatureReport() to send command bytes directly to the hardware.

3. Communicating via WebSerial

Serial communication uses standard JavaScript streams (ReadableStream and WritableStream):

  • Reading Data: The script reads incoming bytes using a stream reader (port.readable.getReader()).
  • Writing Data: The script writes outgoing commands using a stream writer (port.writable.getWriter()).

Accessing Previously Authorized Devices

Once a user has granted permission for a specific device on a domain, the browser remembers this authorization across sessions. The userscript can bypass the selection modal on subsequent page loads by querying existing authorizations using:

  • navigator.hid.getDevices()
  • navigator.serial.getPorts()

If a previously authorized device is already connected, the script can automatically open the port or device connection immediately when loaded, without requiring a new user click.

Execution Context Considerations

Userscripts generally run in an isolated execution context. Depending on the userscript manager and settings:

  • Context Execution: If the script runs in the page's main context (@grant none or window execution), it directly utilizes navigator.hid and navigator.serial.
  • Cross-Origin Restrictions: If the target page is hosted inside an iframe, permission policies (allow="hid" or allow="serial") must be present on the iframe for the APIs to work, regardless of script privileges.
