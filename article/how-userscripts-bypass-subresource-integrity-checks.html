How Userscripts Bypass Subresource Integrity Checks

Subresource Integrity (SRI) is a browser security mechanism that validates external scripts using cryptographic hashes, preventing tampered files from executing on a website. Userscripts—custom code executed via browser extension managers like Tampermonkey or Violentmonkey—handle strict SRI checks by operating outside standard web page execution contexts. They typically resolve SRI conflicts by stripping integrity attributes from injected HTML tags, utilizing built-in metadata directives like @require to fetch dependencies securely, or overriding network API methods before the browser evaluates file hashes.

Stripping Integrity Attributes from the DOM

When a userscript modifies an existing script tag or replaces a remote resource on an SRI-protected website, the browser automatically compares the fetched file against the hash in the integrity attribute. If the script content is modified by the user, the hash validation fails, and the browser blocks execution.

To prevent this, userscripts often intercept the DOM creation process. By removing the integrity attribute before the script element is appended to the document, the browser processes the script as a standard resource without validating its cryptographic signature.

// Example of stripping SRI attributes from injected scripts
const observer = new MutationObserver((mutations) => {
    mutations.forEach((mutation) => {
        mutation.addedNodes.forEach((node) => {
            if (node.tagName === 'SCRIPT' && node.hasAttribute('integrity')) {
                node.removeAttribute('integrity');
            }
        });
    });
});

observer.observe(document.documentElement, { childList: true, subtree: true });

Using Native Userscript Directives (@require and @resource)

Userscript managers handle external dependencies differently than standard web pages. When a user script requires external libraries, it uses the @require or @resource keys in the script's metadata block rather than standard HTML <script> tags.

// ==UserScript==
// @name         SRI Handling Example
// @match        https://example.com/*
// @require      https://code.jquery.com/jquery-3.6.0.min.js
// ==UserScript==

The userscript manager downloads and stores these dependency files locally in the extension's storage upon installation. When the target web page loads, the manager injects the local code directly into the browser's execution context. Because the code is executed locally as an extension asset or raw JavaScript string, it bypasses the page's native network request pipeline and any associated SRI validation rules on the host server.

Overriding Network Request APIs

Some modern web applications perform dynamic asset loading via JavaScript using fetch() or XMLHttpRequest, passing integrity options directly within the fetch calls. Strict SRI policies will fail if the response body does not match the hardcoded hash.

Userscripts overcome this by monkey-patching the global window.fetch or XMLHttpRequest.prototype.open methods. The script intercepts outgoing requests, inspects the request options, and removes the integrity key before the request reaches the network layer.

Alternatively, userscripts can utilize GM_xmlhttpRequest. This API routes network requests through the browser extension's background script rather than the web page's context, bypassing Same-Origin Policy, Content Security Policies (CSP), and SRI checks entirely.

Handling Content Security Policy (CSP) Interactions

SRI is frequently paired with strict Content Security Policies (require-sri-for script). In browser environments where strict CSP prevents unauthorized inline scripts or unverified remote sources, modern userscript managers execute code in an isolated world or use browser extension API privileges (such as declarativeNetRequest or webRequest) to strip CSP and SRI response headers before the web page receives them.
