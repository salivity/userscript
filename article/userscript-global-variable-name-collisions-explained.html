Userscript Global Variable Name Collisions Explained

When two different userscripts attempt to define the same global variable, the actual outcome depends on how the scripts are sandboxed and the method used to declare the variable. In standard userscript environments where sandboxing is enabled, each script operates in its own isolated context, preventing any conflict. However, if both scripts execute in the page's main context or explicitly modify the global window object, the scripts will either overwrite each other's data or cause a JavaScript execution error.

Sandboxed Execution (Default Behavior)

Most modern userscript managers—such as Tampermonkey, Violentmonkey, and Greasemonkey—run scripts inside a safe, isolated sandbox by default.

  • Isolated Scopes: When a script uses default API grants (like GM_getValue or GM_xmlhttpRequest), the manager wraps the code in a private closure.
  • No Collision: If Script A and Script B both declare var userConfig = {}, each script gets its own independent version of userConfig. Neither script can see or interfere with the other's variable.

Unsandboxed Execution (@grant none or window Scope)

If userscripts explicitly opt out of sandboxing (using @grant none) or deliberately attach properties to the page's window object, global variable conflicts will occur. The result depends on how the variable is declared:

1. Overwriting via var or window Properties

If both scripts use var at the top level or attach properties directly to the window object:

  • Script A: window.sharedData = "Script A";
  • Script B: window.sharedData = "Script B";

Outcome: The script that executes last will overwrite the value set by the earlier script. Script A may break or behave unpredictably because its expected global state was changed by Script B.

2. Syntax Errors via let and const

If both scripts inject code into the page's top-level scope (for example, by appending <script> tags to the DOM) using let or const:

  • Script A: let mySettings = { active: true };
  • Script B: let mySettings = { active: false };

Outcome: JavaScript does not allow re-declaration of block-scoped variables in the same scope. The script running second will throw a Uncaught SyntaxError: Identifier 'mySettings' has already been declared and stop executing entirely.

How Execution Order Affects the Outcome

The order in which userscripts run is determined by the browser extension manager and directives like @run-at.

  • First Script: Executes successfully and sets the initial state.
  • Second Script: Either silently overwrites the initial state or throws an error that breaks its own functionality.

Because execution order can vary based on page load speed and script settings, global variable collisions often result in inconsistent, hard-to-debug errors.

Preventing Variable Collisions

To avoid conflicts when writing userscripts:

  1. Maintain Sandboxing: Avoid using @grant none unless strictly necessary.
  2. Use IIFEs: Wrap script code in an Immediately Invoked Function Expression (function() { ... })(); to keep variables out of the global scope.
  3. Namespace Custom Globals: If writing to window is required, group variables under a unique object name (e.g., window.MyUniqueScript_Data).
