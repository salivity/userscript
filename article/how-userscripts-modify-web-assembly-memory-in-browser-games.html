How Userscripts Modify WebAssembly Memory in Browser Games

Userscripts manipulate WebAssembly (Wasm) memory buffers in browser games by intercepting the instantiation of WebAssembly modules, capturing references to their underlying linear memory, and executing real-time read and write operations using JavaScript typed arrays. Because WebAssembly modules rely on a shared WebAssembly.Memory object exposed as an ArrayBuffer, client-side userscripts can bypass game logic to alter variables such as player coordinates, health values, or item counts directly within browser memory.

Intercepting the WebAssembly Instance

Before a userscript can modify game state, it must gain access to the game’s WebAssembly memory instance. Since WebAssembly runs in a sandboxed execution environment, userscripts cannot query internal C/C++ or Rust variables directly by name. Instead, they hook into the JavaScript API methods responsible for loading the Wasm binary.

Userscripts typically monkey-patch WebAssembly.instantiate or WebAssembly.instantiateStreaming early in the page load lifecycle:

const originalInstantiate = WebAssembly.instantiate;
WebAssembly.instantiate = async function(bufferSource, importObject) {
    const result = await originalInstantiate(bufferSource, importObject);
    const instance = result.instance || result;
    
    // Capture exported memory
    window.wasmMemory = instance.exports.memory;
    return result;
};

If the game exports its memory module under exports.memory, capturing this reference gives the script direct access to the WebAssembly.Memory object.

Reading and Writing Linear Memory

WebAssembly memory is stored as a contiguous array of unallocated bytes represented by an ArrayBuffer. To interpret or alter these bytes, userscripts wrap the ArrayBuffer inside JavaScript TypedArrays (such as Uint8Array, Int32Array, or Float32Array) or a DataView.

  • Reading Data: To track dynamic values like player position (often stored as 32-bit floats), the script creates a view over the buffer: 
    const floatView = new Float32Array(window.wasmMemory.buffer);
const playerX = floatView[positionOffset / 4];
  • Writing Data: To modify game logic, the script assigns new values to the specified index: 
    floatView[positionOffset / 4] = 9999.0; // Teleport player

Because JavaScript views mirror the underlying memory buffer, changes made by the userscript instantly affect the game loop running in WebAssembly.

Locating Variable Offsets

Finding the precise memory offsets (addresses) for specific game attributes relies on standard memory scanning techniques:

  1. Initial Scan: The script iterates through the entire memory buffer to find indices matching a known value (e.g., current player health of 100).
  2. Filtered Scan: After the health value changes in-game (e.g., drops to 90), the script scans the previously recorded indices to identify which address holds the updated value.
  3. Pointer Paths: In complex compiled applications, memory addresses are dynamically allocated. Userscripts identify static pointer chains or signature patterns within the Wasm binary to locate dynamic addresses consistently across game sessions.

Managing Buffer Detachment

WebAssembly linear memory can expand at runtime using the memory.grow() instruction. When the memory grows, the original ArrayBuffer is detached, rendering existing TypedArray views invalid.

To prevent runtime errors, userscripts check if the buffer has been detached or instantiate fresh views on every frame update:

function getMemoryView() {
    return new DataView(window.wasmMemory.buffer);
}

function updateGame() {
    const view = getMemoryView();
    // Perform operations safely with updated buffer reference
}

By maintaining valid references to the dynamic memory buffer, userscripts can continuously read, alter, and manipulate WebAssembly browser game data in real time.
