How to Deploy Automated Linting for Userscripts

Automating formatting checks and code analysis for userscripts ensures code quality, prevents runtime errors in browser environments, and maintains standard metadata header structures. This article explores the most common strategies for deploying automated linting for userscripts, ranging from local editor configurations and pre-commit hooks to continuous integration pipelines and custom ESLint rules tailored for browser extension scripts.

1. Local Editor Integration

The first line of defense is integrating linters directly into the code editor (such as Visual Studio Code, Neovim, or WebStorm). By installing tools like ESLint and Prettier alongside their respective editor extensions, developers receive instant visual feedback on syntax errors, formatting inconsistencies, and uninitialized variables as they type.

To support userscripts, local configurations must define browser-specific globals. Adding environments or explicit definitions for userscript APIs (such as GM_getValue, GM_xmlhttpRequest, or unsafeWindow) prevents the linter from incorrectly flagging valid userscript functions as undefined variables.

2. Pre-Commit Git Hooks

Relying on developers to manually fix formatting issues before committing code often leads to inconsistent code repositories. Implementing pre-commit Git hooks automates this step locally before any code reaches the version control system.

Using tools like Husky combined with lint-staged, projects automatically trigger linting and formatting scripts only on the files modified in a commit.

Common workflow:

  • The developer runs git commit.
  • Husky triggers lint-staged.
  • lint-staged runs ESLint and Prettier on changed .user.js files.
  • If errors exist, the commit aborts until the developer resolves them.

3. Continuous Integration (CI) Pipelines

Deploying automated linting in CI services—such as GitHub Actions, GitLab CI, or CircleCI—ensures that unformatted or broken code cannot be merged into the primary repository branch.

A standard CI job pulls the repository, installs dependencies, and runs a headlessly executed linting command (e.g., npm run lint). The pipeline fails if any rules are violated, blocking pull requests until code standards are met. This approach guarantees that even if a contributor disables their local editor rules or git hooks, non-compliant code will not pass review.

4. Userscript-Specific ESLint Plugins

Standard JavaScript linting rules are often insufficient for userscripts due to the unique metadata block required at the beginning of each script (// ==UserScript==). Specialized plugins, such as eslint-plugin-userscript, extend ESLint to validate this metadata block.

Key checks performed by userscript-specific rules include:

  • Verifying required headers like @name, @version, and @match or @include.
  • Catching syntax errors in metadata tags.
  • Ensuring valid URL formats for @icon, @updateURL, and @downloadURL.
  • Warning against grant permissions (@grant) that are declared but unused in the body of the script.

5. Build Tool and Bundler Plugins

Many modern userscripts rely on bundlers like Vite, Rollup, or Webpack to compile TypeScript or modern ES modules into a single final .user.js file. Deploying automated checks directly inside the build process ensures that linting runs automatically whenever a build or development server starts.

Integrating plugins like vite-plugin-eslint or eslint-webpack-plugin aborts the build process if critical errors exist, preventing broken distribution scripts from being generated or published.
