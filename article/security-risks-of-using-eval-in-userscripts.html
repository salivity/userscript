Security Risks of Using eval() in Userscripts

Using eval() in userscripts poses severe security risks, primarily by enabling Arbitrary Code Execution (ACE) and Cross-Site Scripting (XSS) vulnerabilities. Because userscripts run in a privileged or semi-privileged context within the browser, dynamically executing untrusted code can compromise sensitive user data, bypass browser security boundaries, and expose host websites to malicious attacks. This article examines why eval() is dangerous in userscripts, the specific attack vectors involved, and safer alternatives for developers.

The Core Danger of eval()

The eval() function evaluates a string as JavaScript code within the current execution context. In standard web development, eval() is discouraged because it opens vectors for code injection. In userscripts—such as those run via Tampermonkey, Violentmonkey, or Greasemonkey—the risk is amplified because userscripts often operate with elevated permissions that standard web scripts do not possess.

Key Security Implications

1. Privilege Escalation

Userscripts frequently use powerful extension APIs (such as GM_xmlhttpRequest, GM_setValue, or GM_cookie). If a script executes an untrusted string via eval(), an attacker can gain control over these special functions. This allows the injected code to perform cross-origin network requests, read restricted cookies, or alter persistent extension storage.

2. Arbitrary Code Execution (ACE)

If a userscript fetches remote data (like an external configuration file or an API response) and passes it through eval(), any compromise of the remote server or network transport allows an attacker to inject arbitrary code. The injected code will run automatically whenever the userscript executes.

3. Bypassing Content Security Policy (CSP)

Modern websites use Content Security Policies (CSP) to restrict which scripts can run, often blocking inline scripts and eval(). However, userscript managers frequently run scripts in an isolated context that bypasses the page's CSP. Using eval() inside a userscript effectively creates a loophole, allowing dangerous code execution on a page that was otherwise protected by strict security headers.

4. Data Exfiltration and Session Hijacking

Once malicious code executes inside the userscript context, it has full access to the Document Object Model (DOM) of the host page. The attacker can read sensitive information displayed on the screen, capture user inputs (like credentials or credit card numbers), access localStorage and sessionStorage, and exfiltrate this data to a remote server.

Common Scenarios Where eval() Is Misused

  • Parsing Data: Developers sometimes use eval() to parse JSON responses from APIs instead of JSON.parse(). If the response contains executable code rather than plain data, it executes immediately.
  • Dynamic Function Execution: Calling dynamic functions based on user input or page content by evaluating strings (e.g., eval("function_" + input + "()")).
  • Loading Remote Modules: Attempting to dynamically load and run external scripts at runtime by fetching them as text and evaluating them.

Safer Alternatives to eval()

  • Use JSON.parse() for Data: Always use JSON.parse() when processing structured data. It safely converts strings to objects without executing code.
  • Use Object Mapping for Dynamic Code: Replace dynamic code calls with lookup objects or maps: 
    const actions = {
    actionA: () => { /* ... */ },
    actionB: () => { /* ... */ }
};
if (actions[userInput]) {
    actions[userInput]();
}
  • Declare Dependencies Explicitly: In userscripts, use the @require metadata header to import external libraries securely at installation time rather than fetching and evaluating them dynamically at runtime.
