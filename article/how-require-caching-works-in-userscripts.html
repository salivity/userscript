How @require Caching Works in Userscripts

The @require tag in userscripts allows developers to include external JavaScript libraries, such as jQuery or Lodash, into their scripts. Script managers like Tampermonkey, Violentmonkey, and Greasemonkey use a strict caching mechanism for these dependencies, downloading them once during installation and serving them locally thereafter. This article explains how the @require caching system functions, how it impacts script loading speed and reliability, and how to handle updates to required dependencies.

The @require Caching Mechanism

When you install or update a userscript containing @require directives, the script manager fetches the specified remote JavaScript files via HTTP.

Instead of re-fetching these files every time a matching webpage loads, the extension saves the full source code of each required file into browser-level extension storage (typically IndexedDB or WebSQL).

Key characteristics of this mechanism include:

  • One-Time Download: Fetching occurs strictly at installation or update time.
  • Local Injection: During runtime, the cached script text is injected directly into the execution context before your main script runs.
  • Network Bypass: Normal page loads generate zero network requests for the URLs listed in @require headers.

How Caching Affects Userscript Loading

The local caching strategy significantly alters how userscripts execute compared to traditional web development script tags.

1. Instant Execution and Reduced Latency

Because required libraries are stored locally, network speed and latency do not delay script execution. The extension injects the cached code immediately when the target DOM state is met, eliminating rendering delays caused by slow Content Delivery Networks (CDNs).

2. Offline Availability and Reliability

If an external CDN goes down or the user is offline, the userscript continues to function normally. The script manager relies entirely on the local copy, insulating the script from remote host failures or network dropouts.

3. Code Immutability

Remote changes to a required script URL will not automatically propagate to existing users. If a CDN file changes or is compromised, users who already installed the script retain the original version fetched at installation.

How to Update Cached Requirements

Because @require files are cached permanently upon installation, changing the code at a remote URL will not update the file for current users. To force an update to a @require resource, you must use one of the following methods:

  1. Change the Target URL: Append a version query parameter or update the path in the @require header (e.g., // @require https://example.com/lib.js?v=1.1). Script managers treat a new URL as a new resource and download it.
  2. Increment the Userscript @version: Updating the main script's @version header prompts the script manager to re-check and re-download all associated @require dependencies during the update cycle.
  3. Manual Reinstallation: Users can manually reinstall the userscript or clear the script manager's cache to force fresh downloads of all dependencies.
