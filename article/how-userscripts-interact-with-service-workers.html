How Userscripts Interact with Service Workers

Userscripts and Service Workers operate at different execution layers of a web application, creating a unique dynamic in how they interact. While userscripts execute within the DOM context of a web page to modify user interfaces and browser behavior, Service Workers run in a separate background thread handling network caching, offline support, and push notifications. Understanding how userscripts interact with Service Workers requires looking at execution contexts, script execution timing, network request interception, and API messaging protocols.

Execution Context and Scope Isolation

Service Workers run in a dedicated global context (ServiceWorkerGlobalScope) that completely lacks access to the DOM, the window object, and webpage-level JavaScript variables. Userscripts, managed by extensions like Tampermonkey or Violentmonkey, run in a content script environment that has direct access to the webpage DOM and can manipulate the main thread's window object.

Because of this context isolation, a userscript cannot directly inject code into a running Service Worker thread or inspect its internal variables. Interaction must occur indirectly through exposed browser APIs, network event hooks, or message-passing interfaces.

Intercepting Service Worker Registration

A primary method userscripts use to control or alter Service Workers is intercepting their registration process. When a webpage registers a Service Worker, it calls navigator.serviceWorker.register('/sw.js').

If a userscript is configured to run early—specifically at @run-at document-start—it can monkey-patch the registration method before the page executes its own scripts:

const originalRegister = navigator.serviceWorker.register;
navigator.serviceWorker.register = function(scriptURL, options) {
    console.log('Intercepted Service Worker registration:', scriptURL);
    // Modify the scriptURL, change options, or return a canceled Promise
    return originalRegister.apply(this, arguments);
};

By hooking this API, a userscript can:

  • Prevent Registration: Block the registration of specific Service Workers by returning a rejected promise or doing nothing.
  • Redirect Script URLs: Swap the site's default Service Worker file with a modified custom version hosted elsewhere.
  • Inspect Options: Alter parameters such as the Service Worker's scope.

Network Request Flow and Bypassing Caches

Service Workers intercept outbound network requests using the fetch event listener to serve cached assets or modify requests. The interaction between userscripts and Service Workers during network activity depends on how the userscript initiates its requests:

  1. Standard Page Fetch (window.fetch / XMLHttpRequest): When a userscript calls the page's native fetch() or XMLHttpRequest, the request flows through the active Service Worker. The Service Worker can intercept, modify, or serve the request from its local cache.
  2. Userscript Privileged APIs (GM_xmlhttpRequest): When a userscript uses custom extension APIs like GM_xmlhttpRequest or GM.xmlHttpRequest, the request bypasses the webpage context entirely. It is routed directly through the browser extension's background process, completely bypassing any active Service Workers and their fetch event handlers.

Messaging Between Userscripts and Service Workers

Direct communication between a userscript and an active Service Worker is possible using the Web Channel API (postMessage).

Page to Service Worker

If the target webpage's Service Worker is designed to listen for messages, a userscript running in the page context can transmit data to it via the active controller:

if (navigator.serviceWorker.controller) {
    navigator.serviceWorker.controller.postMessage({
        type: 'CUSTOM_USERSCRIPT_EVENT',
        payload: { key: 'value' }
    });
}

Listening for Worker Responses

Userscripts can also listen for broadcasts or messages emitted by the Service Worker back to the page:

navigator.serviceWorker.addEventListener('message', (event) => {
    console.log('Message received from Service Worker:', event.data);
});

Disabling Service Workers via Userscripts

In scenarios where a Service Worker interferes with userscript modifications by aggressively serving cached scripts or HTML, userscripts can proactively unregister active workers.

navigator.serviceWorker.getRegistrations().then((registrations) => {
    for (let registration of registrations) {
        registration.unregister();
        console.log('Unregistered Service Worker:', registration);
    }
});

To ensure the Service Worker does not immediately re-register upon page load, this unregistration logic is usually combined with the navigator.serviceWorker.register monkey-patching technique described above.
