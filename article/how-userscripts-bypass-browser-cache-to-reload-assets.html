How Userscripts Bypass Browser Cache to Reload Assets

Userscripts execute within the web browser to alter web page content and functionality, but they often encounter stale content due to aggressive browser caching. To force asset reloading, userscripts cannot directly clear the browser's internal storage; instead, they manipulate resource request URLs, alter HTTP headers, and override native JavaScript fetching methods. This article explains the technical mechanisms userscripts use to force the browser into fetching fresh assets directly from the web server.

Cache-Busting via Query Parameters

The primary method a userscript uses to force asset reloading is cache-busting. Web browsers store and retrieve cached assets using the exact resource URL as the key. By appending a dynamically generated parameter to the URL, the userscript tricks the browser into seeing the asset as an entirely new resource.

When modifying elements like <img>, <link>, or <script>, the userscript appends a unique value, such as a UNIX timestamp or a random string, to the URL:

  • Original URL: https://example.com/styles.css
  • Modified URL: https://example.com/styles.css?t=1672531199000

Because the modified URL creates a new cache key, the browser bypasses its local cache and issues a direct network request to the server.

Overriding Native Fetch and XMLHttpRequest

Userscripts running at document-start can hook into or replace the browser's native networking APIs (window.fetch and XMLHttpRequest). By monkey-patching these APIs, the userscript intercepts every network request initiated by the page.

Inside the overridden functions, the userscript can:

  1. Automatically append cache-busting query strings to all outbound requests.
  2. Set custom HTTP request headers, such as Cache-Control: no-cache or Pragma: no-cache.

When a request includes these Cache-Control directives, the browser's network stack bypasses the local disk and memory cache, demanding a fresh response or revalidation from the remote server.

Leveraging Extension APIs (GM_xmlhttpRequest)

Userscript managers (such as Tampermonkey or Violentmonkey) provide privileged APIs like GM_xmlhttpRequest. Unlike standard page scripts constrained by browser security models, GM_xmlhttpRequest executes within the extension's background context.

This grants the script direct control over request headers and caching behavior. A userscript can execute a request with specific headers:

  • Cache-Control: no-cache, no-store, must-revalidate
  • Pragma: no-cache

Once GM_xmlhttpRequest fetches the updated asset from the network, the userscript can convert the payload into a Blob URL or inline base64 string and inject it directly into the web page, fully replacing the browser's cached asset.

DOM Node Removal and Re-injection

For scripts, stylesheets, or images embedded static in the original HTML, userscripts force reloads by removing the existing DOM nodes and re-creating them.

The userscript performs the following sequence:

  1. Locates the targeted target element (e.g., <script src="app.js">).
  2. Removes the element from the DOM to stop execution or rendering.
  3. Creates a new DOM element of the same type.
  4. Assigns the source attribute with an added cache-busting parameter.
  5. Re-attaches the element to the <head> or <body>.

This forces the browser's HTML parser and renderer to treat the element as a newly inserted node, prompting an immediate background fetch for the updated asset.
