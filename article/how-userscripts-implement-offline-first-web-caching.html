How Userscripts Implement Offline-First Web Caching

Offline-first caching in userscripts allows browser extensions like Tampermonkey or Violentmonkey to store web-scraped data locally, enabling immediate data availability even without an active internet connection. By leveraging browser storage APIs and script manager functions, userscripts check local caches before making external network requests, drastically improving load speeds, bypassing rate-limiting issues, and enabling seamless offline functionality.

Core Storage Mechanisms

To store scraped web data locally, userscripts rely on three primary storage interfaces depending on data volume, security, and persistence requirements.

1. Script Manager Storage (GM_setValue / GM.setValue)

The standard approach for userscripts is using the script manager's dedicated API (GM_setValue for synchronous legacy scripts or GM.setValue for modern promise-based scripts).

  • Cross-Domain Persistence: Unlike standard Web Storage APIs, GM_setValue can share cached data across different websites if the script runs on multiple domains.
  • Isolation: Data is stored inside the extension's environment, preventing the host website from accessing, modifying, or clearing the cached scrapings.

2. Browser LocalStorage API

For basic key-value data where scraping occurs and stays on a single domain, the native window.localStorage API offers a simple solution.

  • Pros: Built directly into JavaScript, easy to implement with zero dependency on script manager permissions.
  • Cons: Limited storage cap (typically 5MB per origin) and accessible to the web page's native scripts.

3. IndexedDB

For high-volume scraping tasks—such as caching thousands of records, large JSON objects, or media blobs—userscripts utilize IndexedDB.

  • Pros: Capable of storing hundreds of megabytes of structured data asynchronously with indexed search capabilities.
  • Cons: Requires asynchronous database connections and more complex code to query compared to key-value stores.

The Offline-First Execution Workflow

An offline-first userscript uses a structured execution order to prioritize locally stored data over live web requests:

  1. Cache Read Request: When a target page loads, the script generates a cache key based on the page URL, item ID, or DOM selector.
  2. Availability & Validity Check: The script reads the cached entry and inspects metadata (such as an embedded timestamp) to verify if the data exists and is fresh.
  3. Immediate Local Render: If valid cached data exists, the userscript immediately injects it into the DOM without touching the network.
  4. Network Fallback: If the cache is empty, corrupted, or expired, the script performs a fetch request or scrapes the active DOM.
  5. Cache Refresh: The newly scraped content is stored locally alongside a fresh timestamp for future offline requests.

Cache Expiration and Invalidation Strategies

To prevent serving obsolete information and to keep storage within browser limits, userscripts implement explicit cache maintenance routines:

  • Time-To-Live (TTL) Wrappers: Scraped data is saved inside a wrapper object containing the payload and the creation timestamp: 
    {
  "timestamp": 1710000000000,
  "payload": { "title": "Example", "price": "$19.99" }
}
  • Stale-While-Revalidate: The script renders the old cached data instantly so the user sees content immediately, then silently scrapes fresh data in the background to update the cache for the next page load.
  • LRU (Least Recently Used) Eviction: When local storage fills up, the userscript deletes the oldest or least-accessed records to make space for new web scrapes.
