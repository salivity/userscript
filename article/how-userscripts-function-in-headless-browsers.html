How Userscripts Function in Headless Browsers

Userscripts modify web pages by injecting custom JavaScript into the browser runtime, altering page behavior, layout, or functionality. In a headless browser environment—where a browser runs without a graphical user interface—userscripts operate programmatically through automation frameworks like Puppeteer, Playwright, or Selenium. This article explains how headless environments load and execute userscripts, how DOM context isolation works, and the core mechanisms required to manage script execution during automated tasks.

Script Injection Mechanisms

Traditional browser extensions like Tampermonkey or Violentmonkey automatically detect metadata headers (such as @match or @run-at) and inject scripts into web pages. Headless browsers typically run without extensions enabled by default. Instead, developers manually replicate script injection using automation APIs.

Automation frameworks handle userscripts using two primary execution methods:

  • Pre-load Injection: Scripts are registered to execute before the target web page's scripts run. In Puppeteer, this is achieved using page.evaluateOnNewDocument(), while Playwright uses page.addInitScript(). This method is essential for userscripts that rely on @run-at document-start to modify window properties or intercept network requests early.
  • Post-load Execution: Scripts are injected after the DOM has fully rendered or reached a specific loading state (such as @run-at document-idle). Frameworks execute these using methods like page.evaluate() or by appending a <script> tag directly into the DOM tree.

Execution Context and Isolation

When a userscript runs in a headless browser, it operates within the context of the target web page's JavaScript runtime. Understanding the execution context is crucial for predictable functionality:

  1. DOM Access: Userscripts have full access to the page's Document Object Model (DOM). They can query elements, attach event listeners, alter CSS styles, or trigger clicks programmatically.
  2. Global Scope: Unlike node scripts driving the automation, userscripts run inside the browser instance. Variables declared in the userscript live within the page's window object unless explicitly contained within an IIFE (Immediately Invoked Function Expression) or a block scope.
  3. Security Restrictions (CORS & CSP): In a graphical browser, extension managers bypass strict Content Security Policies (CSP) and Cross-Origin Resource Sharing (CORS) restrictions. In a headless browser using plain injection, native scripts might be blocked by CSP header policies unless the headless browser is configured to bypass web security flags (e.g., --disable-web-security).

Handling Special GM_* APIs

Standard userscripts often rely on Tampermonkey-specific APIs, such as GM_getValue, GM_setValue, or GM_xmlhttpRequest. In a headless browser without an extension manager installed, these APIs do not exist natively.

To run scripts that depend on these functions, developers must provide shim implementations before the userscript executes:

  • Storage Emulation: GM_getValue and GM_setValue can be polyfilled using the browser's native localStorage API or mapped to host-level database calls.
  • Cross-Domain Requests: GM_xmlhttpRequest can be replaced with native fetch() calls or intercepted at the browser framework level using request interception features provided by Playwright or Puppeteer.

Workflow of Userscript Execution

The lifecycle of a userscript in a headless environment follows a defined path:

  1. Browser Initialization: The automation tool launches a headless browser instance (e.g., Chromium, Firefox, or WebKit).
  2. Script Registration: The userscript file is read from the file system and registered with the browser context using pre-load functions.
  3. Page Navigation: The headless browser navigates to the target URL (page.goto()).
  4. Script Trigger: As the page loads, the browser engine executes the injected userscript code automatically at the designated lifecycle event.
  5. Result Retrieval: The automation host extracts any modified data, logs, or state changes produced by the userscript using evaluation promises.
