Userscripts and WebAuthn API for Passwordless Login

This article provides an overview of how userscripts interact with the Web Authentication API (WebAuthn) to facilitate, inspect, or modify passwordless login flows. It covers the browser security boundaries governing WebAuthn, how userscripts operate within the page context to interact with credential requests, common use cases like testing and debugging, and the security implications of manipulating hardware-bound authentication.

Understanding the WebAuthn API Context

The Web Authentication API (navigator.credentials) is a web standard that enables servers to register and authenticate users using public-key cryptography instead of passwords. It relies on hardware authenticators, such as security keys (YubiKeys), Touch ID, Face ID, or Windows Hello.

Because WebAuthn operates directly within the browser standard, it is subject to strict security constraints, specifically the Same-Origin Policy. Credentials generated via WebAuthn are bound to a specific Relying Party ID (RP ID), which typically corresponds to the website's domain name.

How Userscripts Execute Relative to WebAuthn

Userscripts (executed via browser extensions like Tampermonkey, Violentmonkey, or Greasemonkey) run inside the context of the target web page. Depending on the script manager's settings, a userscript may run in an isolated execution environment (isolated world) or directly in the page's main execution context (page world).

Because WebAuthn methods live on the global navigator.credentials object, userscripts have full access to inspect, override, or call these APIs within the context of the domain where the script is running.

Key Touchpoints Between Userscripts and WebAuthn

  1. API Interception and Wrapping: Userscripts can redefine navigator.credentials.create() (used during registration) and navigator.credentials.get() (used during login). By wrapping these functions, a userscript can inspect the challenge data, Relying Party options, and public key parameters being passed between the web application and the browser.

  2. Automating UI Workflows: While userscripts cannot bypass the hardware interaction requirement (such as tapping a physical YubiKey or scanning a fingerprint), they can automate all surrounding web page elements. A script can automatically click "Sign in with Passkey," select user profiles, or fill in non-sensitive username fields before triggering the native WebAuthn prompt.

  3. Mocking and Virtual Authenticators: For development and testing, userscripts can completely mock the navigator.credentials object. By intercepting calls to get() or create(), a userscript can return pre-defined public key credentials or simulated responses without triggering actual hardware security prompts, allowing developers to test frontend fallback states and error handling.

  4. Debugging and Telemetry: Userscripts are commonly used to log raw WebAuthn payloads to the developer console. Because public keys, credential IDs, and client data JSON objects are encoded as ArrayBuffer objects, userscripts can automatically decode base64url data to aid in troubleshooting authentication parameters.

Security Boundaries and Limitations

While userscripts can manipulate the JavaScript API surface, they operate under strict security limitations enforced by the browser engine:

  • No Access to Private Keys: The underlying private keys created during WebAuthn registration are stored securely inside the hardware authenticator or operating system keychain. Neither the host webpage nor a userscript can ever extract or view these keys.
  • User Activation Requirements: The WebAuthn specification requires transient activation (a physical user gesture like a button click) to invoke authentication calls. Userscripts attempting to invoke navigator.credentials.get() without an active user event may be rejected by the browser.
  • Domain Binding Integrity: A userscript running on example.com cannot issue WebAuthn requests on behalf of google.com. The browser enforces the Relying Party origin checks at a native level, preventing cross-origin passkey spoofing.

Userscripts serve as a powerful interface for automating, monitoring, and debugging WebAuthn passwordless flows, but the core cryptographic trust model remains protected by browser-level origin enforcement and hardware security modules.
