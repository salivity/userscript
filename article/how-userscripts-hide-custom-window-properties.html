How Userscripts Hide Custom Window Properties

Modern web applications often inspect the global window object to detect unauthorized browser extensions, anti-adblock bypasses, or custom automation scripts. Userscripts prevent detection of their custom properties by keeping variables out of the shared global scope, leveraging browser-level context isolation, manipulating property descriptors, and using Proxy objects to conceal modifications from native page scripts.

Browser-Level Isolated Worlds

The primary defense mechanism used by userscript managers like Tampermonkey and Violentmonkey is browser context isolation, commonly referred to as "Isolated Worlds."

In modern browsers, userscripts run in a distinct execution context separate from the main web page's JavaScript context:

  • Shared DOM Access: Both the website script and the userscript share access to the document object model (DOM), allowing DOM modifications.
  • Separated JavaScript Objects: The userscript operates on its own global window instance. Any property attached to the global scope (e.g., window.myCustomValue = true) exists strictly within the userscript's context and is entirely invisible to scripts running in the page's main context.

Closure Scoping and IIFEs

When scripts must run directly within the page's main execution context (for instance, when using @grant none or injecting raw <script> tags), developers avoid attaching variables directly to the window object. Instead, they wrap execution logic inside Immediately Invoked Function Expressions (IIFEs) or module blocks.

(function() {
    // Local variable confined to this closure
    const customConfig = { hidden: true };
    
    // Page scripts inspecting window cannot see 'customConfig'
})();

By relying on lexical scoping, variables remain stored safely within function memory rather than polluting the global namespace.

ES6 Proxies and Property Traps

For advanced use cases where a script must modify existing window properties or inject dynamic behaviors, ES6 Proxy objects can intercept detection routines.

If a website attempts to detect modifications by using methods like Object.getOwnPropertyNames(window) or hasOwnProperty(), a custom Proxy trap can intercept these calls and filter out the user-defined keys:

const originalWindow = window;
window = new Proxy(originalWindow, {
    get(target, prop, receiver) {
        if (prop === 'detectedCustomProperty') {
            return undefined; // Hide the property on read
        }
        return Reflect.get(target, prop, receiver);
    },
    has(target, prop) {
        if (prop === 'detectedCustomProperty') {
            return false; // Hide property from 'in' operator checks
        }
        return Reflect.has(target, prop);
    }
});

Overriding Property Descriptors

Websites often check for modifications by inspecting object property descriptors via Object.getOwnPropertyDescriptor(). Userscripts counter this by fine-tuning property attributes using Object.defineProperty().

By explicitly setting the enumerable attribute to false, userscripts prevent custom properties from appearing during for...in loops, Object.keys(), or JSON.stringify() scans:

Object.defineProperty(window, 'hiddenProperty', {
    value: 'secret',
    writable: true,
    configurable: true,
    enumerable: false // Prevents detection in standard property enumerations
});

Cloaking Native Method Overrides

If a userscript overrides a native window function (such as fetch or XMLHttpRequest), anti-tamper scripts may check the function's string representation using .toString(). Native browser functions return function () { [native code] }.

Userscripts prevent detection by overriding the toString method of modified functions to spoof native signatures:

function cloakNative(customFunc, originalFunc) {
    customFunc.toString = function() {
        return originalFunc.toString();
    };
    return customFunc;
}

window.fetch = cloakNative(function(...args) {
    // Custom logic here
    return originalFetch.apply(this, args);
}, originalFetch);

By combining execution context isolation with defensive JavaScript patterns, userscripts effectively insulate their internal state and hide modifications from client-side detection scripts.
