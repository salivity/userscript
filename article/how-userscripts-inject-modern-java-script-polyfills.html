How Userscripts Inject Modern JavaScript Polyfills

Userscripts can enhance legacy websites by injecting polyfills—code snippets that emulate modern JavaScript APIs and features unsupported by older browser environments or outdated site frameworks. By leveraging userscript manager directives like @require, execution hooks such as @run-at document-start, or dynamic DOM script injection, developers can load polyfill libraries (like core-js) before the target site scripts execute. This article explains the technical mechanisms userscripts use to inject polyfills, manage window scope isolation, and restore modern web functionality to legacy pages.

Understanding Polyfills in the Context of Userscripts

A polyfill is code that implements a feature on web browsers that do not natively support it. Legacy websites or outdated web views often lack modern JavaScript methods (such as Array.prototype.at(), Object.fromEntries(), or the fetch() API).

Userscripts run via browser extensions (such as Tampermonkey, Violentmonkey, or Greasemonkey) to modify web pages. When a userscript targets an older site, it can inject these missing features directly into the browser's execution context, allowing both the script itself and the underlying site to use modern syntax and APIs.

Method 1: Injecting Polyfills via the @require Metadata Block

The cleanest and most common way to add polyfills to a userscript is using the @require header in the metadata block. Userscript engines automatically download the requested external script and prepend its execution to the userscript.

// ==UserScript==
// @name         Legacy Site Modernizer
// @namespace    http://tampermonkey.net/
// @version      1.0
// @match        https://legacy-example.com/*
// @run-at       document-start
// @require      https://cdnjs.cloudflare.com/ajax/libs/core-js/3.32.0/minified.js
// ==UserScript==

// Modern JS features are now available within the userscript context
const data = [10, 20, 30];
console.log(data.at(-1)); // Output: 30

Setting @run-at document-start ensures that the polyfill loads before the DOM is fully constructed and before any site scripts attempt to execute.

Method 2: Dynamic Script Injection into the Page Context

By default, userscripts execute inside an isolated context (a sandbox) separate from the main web page. While @require polyfills the userscript's isolated scope, it may not polyfill the actual page's global window object.

To make polyfills available to the host website's original scripts, the userscript must dynamically insert a <script> element directly into the DOM context.

(function() {
    'use strict';

    const script = document.createElement('script');
    script.src = 'https://cdnjs.cloudflare.com/ajax/libs/core-js/3.32.0/minified.js';
    script.onload = () => {
        console.log('Polyfills successfully loaded into the main page context.');
    };
    (document.head || document.documentElement).appendChild(script);
})();

This method attaches the polyfilled methods directly to the host page's global window scope, enabling legacy scripts on the page to use modern features without throwing TypeError or Undefined exceptions.

Method 3: Polyfilling via unsafeWindow

For userscript managers that support the GM_info or unsafeWindow API, developers can attach missing methods directly to the host page's window object from within the sandbox context.

// ==UserScript==
// @name         Fetch API Polyfill Injector
// @match        https://legacy-example.com/*
// @grant        unsafeWindow
// ==UserScript==

if (!unsafeWindow.fetch) {
    // Assign a polyfilled fetch implementation to the main page window
    unsafeWindow.fetch = function(url, options) {
        return new Promise((resolve, reject) => {
            const xhr = new XMLHttpRequest();
            xhr.open(options?.method || 'GET', url);
            xhr.onload = () => resolve(new Response(xhr.responseText, { status: xhr.status }));
            xhr.onerror = () => reject(new TypeError('Network request failed'));
            xhr.send(options?.body);
        });
    };
}

Polyfills vs. Transpilation for Syntax Support

It is important to distinguish between API polyfills and syntax transpilation:

  • API Polyfills: Add missing runtime functions or methods (e.g., Promise, fetch, String.prototype.replaceAll). These can be injected at runtime using the methods outlined above.
  • Syntax Transpilation: Older JavaScript engines cannot parse modern syntax constructs (e.g., optional chaining ?., nullish coalescing ??, or arrow functions () => {}).

If the target browser itself is too old to parse modern syntax, injecting a polyfill script at runtime will not prevent syntax errors. In these cases, the userscript source code must be transpiled down to ES5 using tools like Babel prior to installing it in the userscript manager.
