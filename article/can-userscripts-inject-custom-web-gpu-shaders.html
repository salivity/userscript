Can Userscripts Inject Custom WebGPU Shaders?

Userscripts can successfully inject custom WebGPU shaders into browser-based rendering engines by intercepting and modifying JavaScript API calls before the shaders are compiled. By monkey-patching native WebGPU methods like GPUDevice.prototype.createShaderModule, custom scripts can alter WGSL (WebGPU Shading Language) code dynamically to modify graphics, inject post-processing shaders, or tweak game visuals directly inside the user's browser.

How WebGPU Shader Injection Works

WebGPU operates through standard JavaScript bindings exposed by the browser via the navigator.gpu object. Because userscripts run within the context of the webpage, they share the same execution environment and can manipulate WebGPU API functions before the target application creates its rendering pipelines.

The injection process relies on a technique called API hooking or monkey-patching:

  1. Interception: The userscript intercepts calls to GPUDevice.prototype.createShaderModule.
  2. Inspection: The script reads the incoming GPUShaderModuleDescriptor object containing the raw WGSL shader source code.
  3. Modification: The script replaces, modifies, or appends custom WGSL code (such as custom vertex transformations, fragment color adjustments, or lighting effects).
  4. Execution: The script calls the original native createShaderModule method with the modified shader string, passing the altered graphics code to the GPU.

Step-by-Step Mechanism

To intercept shader creation, a userscript typically hooks into the pipeline during early page load using the @run-at document-start directive.

// Example of monkey-patching WebGPU shader creation
const originalCreateShaderModule = GPUDevice.prototype.createShaderModule;

GPUDevice.prototype.createShaderModule = function (descriptor) {
    // Check if the descriptor contains WGSL code
    if (descriptor && descriptor.code) {
        // Search for specific fragment shader functions and append custom code
        if (descriptor.code.includes("fn main")) {
            descriptor.code = descriptor.code.replace(
                "return finalColor;",
                "return finalColor * vec4<f32>(1.2, 1.0, 0.8, 1.0);" // Injects custom tint
            );
        }
    }
    // Call the native browser method with modified WGSL code
    return originalCreateShaderModule.apply(this, arguments);
};

Beyond altering existing shaders, a userscript can also create entirely new WebGPU render passes. By wrapping GPUCanvasContext.prototype.configure or hooking into the frame render loop (requestAnimationFrame), a script can bind custom render pipelines to draw post-processing passes (such as bloom, CRT filters, or custom depth effects) on top of the engine's output.

Practical Applications

  • Browser Game Modding: Customizing character shaders, lighting models, or visual effects in WebGPU-powered games built with modern engines like Three.js, Babylon.js, or PlayCanvas.
  • Post-Processing Injection: Adding full-screen visual shaders (e.g., FXAA, color grading, scanlines) to web applications that lack built-in graphics settings.
  • Debugging and Graphics Research: Inspecting, dumping, and analyzing raw WGSL shaders used by web applications in real-time.
  • Accessibility Adjustments: Enhancing contrast, colorblindness modes, or removing bright flashing visual elements dynamically.

Challenges and Technical Limitations

While shader injection is entirely possible, several technical obstacles exist:

  • Timing Constraints: The userscript must execute before the target application initializes its WebGPU device. If the application caches its shader modules early, late-running scripts will fail to intercept them.
  • WGSL Parsing Complexity: Modern web applications often minify or procedurally generate WGSL code. Finding the right hooks or function names inside minified shader strings requires regex matching or abstract syntax tree (AST) parsing.
  • Pipeline Layout Mismatches: Changing shader input/output structures (bind groups, uniforms, or vertex buffers) without updating the corresponding GPURenderPipeline layout will cause WebGPU validation errors and halt rendering.
  • CORS and Resource Assets: Loading external textures or resources for custom shaders must comply with browser Cross-Origin Resource Sharing rules.
