Userscript @Match Syntax for Subdomains

The @match directive in userscript managers like Tampermonkey, Violentmonkey, and Greasemonkey allows developers to target specific web pages by defining URL pattern rules. While many developers assume @match accepts full Regular Expressions (Regex), it actually uses a standardized, simplified wildcard syntax strictly divided into scheme, host, and path components. This article explains the exact pattern syntax for targeting complex subdomains using @match, its inherent limitations, and how to use standard Regex with @include when advanced subdomain filtering is required.

Standard @match Syntax Rules

A valid @match rule consists of three distinct parts: <scheme>://<host>/<path>

  1. Scheme: Must be http, https, file, ftp, urn, or an asterisk * (which matches both http and https).
  2. Host: Specifies the domain or subdomain. It can be an exact hostname, a single * (matching any host), or start with *. to match a domain and all of its subdomains.
  3. Path: Must begin with a forward slash / and can contain wildcards (*) anywhere in the path string.

Targeting Subdomains with @match

To target subdomains using @match, you must follow strict wildcard placement rules:

  • Targeting all subdomains (including root): // @match *://*.example.com/* Matches: example.com, sub.example.com, deep.nested.sub.example.com.

  • Targeting a specific explicit subdomain: // @match https://app.example.com/* Matches: app.example.com exclusively.

Syntax Limitations in @match

Unlike full Regular Expressions, the @match directive imposes strict limitations on where wildcards can appear in the host portion:

  • No mid-string wildcards in host: You cannot place a wildcard in the middle of a hostname. Invalid: // @match https://dev-*.example.com/*
  • No multi-level wildcard prefixes: You cannot use multiple wildcards in the host. Invalid: // @match https://*.*.example.com/*
  • No regular expression tokens: Character classes, quantifiers, and anchors like [a-z], \d, or + are treated as literal characters, not regex logic.

Complex Subdomain Targeting with Regex (@include)

If your project requires true Regular Expression matching for complex subdomain structures (such as matching specific numerical dynamic subdomains like tenant-123.example.com), you should use the @include directive instead of @match.

When an @include parameter is wrapped in forward slashes (/), userscript managers evaluate it as a full JavaScript Regular Expression:

// @include /^https?:\/\/(dev|stage|app-\d+)\.example\.com\/.*$/

This pattern explicitly targets:

  • Scheme: http or https
  • Host: dev.example.com, stage.example.com, or any numbered dynamic subdomain like app-12.example.com
  • Path: Any path following the host
