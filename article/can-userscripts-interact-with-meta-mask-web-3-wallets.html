Can Userscripts Interact With MetaMask Web3 Wallets?

Userscripts can interact with Web3 wallet extensions like MetaMask because these wallets inject global JavaScript objects into the webpage's Document Object Model (DOM). By accessing these injected objects—most notably window.ethereum—userscripts can detect wallet connections, request accounts, read network data, and trigger transaction signatures. This article details how this interaction works, execution context considerations, common use cases, and the associated security risks.

How Userscripts Access Injected Web3 Providers

When a browser extension like MetaMask is enabled, it automatically injects an Ethereum provider object into the global scope of every webpage (or pages authorized by the user). This object, standardly exposed as window.ethereum, serves as the bridge between the webpage and the wallet extension.

Because userscripts execute within the context of the loaded webpage, they can reference this injected provider to communicate with the wallet. A basic userscript can execute standard Web3 methods such as window.ethereum.request({ method: 'eth_requestAccounts' }) to trigger the wallet popup.

Execution Contexts and unsafeWindow

Browser script managers (such as Tampermonkey or Violentmonkey) run userscripts in an isolated context to prevent page scripts from modifying the userscript's variables. Depending on how the script manager handles DOM isolation, accessing the injected Web3 provider requires specific setup:

  • Direct Access (@grant none): If a userscript does not request special API privileges, it runs in the main window context and can directly read window.ethereum.
  • Isolated Context (unsafeWindow): If a script uses @grant directives (like GM_xmlhttpRequest), it runs in a sandbox. To access the page's global variables in this state, the script must reference unsafeWindow.ethereum instead of window.ethereum.
  • Script Injection: Alternatively, a userscript can dynamically create and append a standard <script> element to the document body to run native Web3 JavaScript within the page's original execution environment.

What Userscripts Can and Cannot Do

Capabilities

  • Read Public Data: Userscripts can query the user's active wallet address, current network chain ID, and account balances.
  • Initiate Actions: Userscripts can programmatically trigger wallet prompts for network switches, token imports, message signatures, and smart contract transactions.
  • Automate UI Workflows: Userscripts can combine standard dApp interactions with wallet calls, streamlining repetitive actions on Web3 interfaces.

Limitations

  • No Direct Access to Private Keys: Userscripts operate entirely outside the browser extension's secure storage. They cannot access private keys, seed phrases, or wallet passwords.
  • Mandatory User Authorization: A userscript cannot execute transactions or sign messages silently. Every transaction request generated by a userscript forces the wallet extension interface to pop up, requiring explicit approval from the user.

Security Considerations

While userscripts cannot directly steal private keys, running untrusted or malicious userscripts on Web3-enabled pages introduces risk. A malicious userscript can attempt to display fake dApp interfaces, alter transaction parameters (such as changing the destination address or token amount), or repeatedly trigger signature prompts in an effort to trick the user into approving a malicious transaction. Users should only install userscripts from trusted sources and carefully review transaction details inside the wallet confirmation window before approving any request.
