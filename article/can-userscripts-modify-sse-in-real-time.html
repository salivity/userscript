Can Userscripts Modify SSE in Real-Time?

Yes, userscripts can parse and modify Server-Sent Events (SSE) in real-time, though doing so requires intercepting the browser's native network APIs before the target webpage establishes the stream connection. Because userscripts run on the client side, they can override the global EventSource object or the underlying fetch/XMLHttpRequest implementations to read, filter, or alter incoming event data streams before the host website processes them.

Intercepting Standard EventSource Objects

The standard API for receiving Server-Sent Events in JavaScript is the EventSource interface. To modify these events in real-time, a userscript must replace the global window.EventSource constructor with a custom wrapper or Proxy.

When the target website instantiates a new EventSource, the intercepted constructor creates the real connection internally while wrapping the event listeners. The userscript then intercepts the incoming onmessage callback or addEventListener('message', ...) calls. Inside the listener wrapper, the script parses the event.data payload (often JSON), modifies the content, and constructs a new synthetic MessageEvent to dispatch to the original page listeners.

Handling Fetch and Stream-Based SSE

Many modern web applications implement SSE streams using the fetch API combined with a ReadableStream reader instead of the native EventSource interface. In these cases, monkey-patching EventSource will not work.

To intercept stream-based SSE, the userscript must override window.fetch. When a request targeting an SSE endpoint is detected (typically identified by the Accept: text/event-stream header or a specific URL pattern), the custom fetch function intercepts the Response.body. The script reads the binary chunks, decodes the raw text, parses the SSE format (lines prefixed with data:), alters the string payload, and re-encodes the data into a new TransformStream or custom ReadableStream passed back to the web application.

Context and Timing Requirements

For SSE interception to succeed, two execution conditions must be met:

  1. Execution Timing: The userscript must run before the application script executes its network calls. This is achieved by setting the metadata directive @run-at document-start.
  2. Execution Context: Extensions and userscript managers often execute scripts in an "isolated world" separate from the main page's JavaScript context. To intercept the global EventSource or fetch APIs used by the page, the script must target the main world context (for instance, by accessing unsafeWindow in Tampermonkey/Violentmonkey or injecting a inline <script> tag directly into the DOM).
