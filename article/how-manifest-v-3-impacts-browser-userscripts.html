How Manifest V3 Impacts Browser Userscripts

The transition from Manifest V2 to Manifest V3 significantly alters how browser extensions handle custom userscripts, primarily due to stricter security policies and architectural API changes. By banning remotely hosted code and replacing persistent background pages with short-lived service workers, Manifest V3 restricts dynamic code execution, forcing popular extensions like Tampermonkey and Violentmonkey to rewrite their core engines. While userscripts will not completely disappear, users will experience changes in how scripts are installed, executed, and restricted within Chromium-based browsers.

Ban on Dynamic Code Execution

Manifest V3 introduces a strict rule against executing remotely hosted code. In Manifest V2, userscript managers could easily download a script from an external URL and execute it on the fly using functions like eval() or dynamic script tag injections.

Under Manifest V3, arbitrary code execution from external sources is banned to prevent malicious extensions from pulling dangerous payloads after passing Chrome Web Store review. Because userscripts are inherently dynamic external code, standard injection techniques no longer work without specific browser-level permissions.

The Dedicated userScripts API

To prevent userscript managers from becoming completely obsolete, browser vendors introduced the dedicated userScripts API for Manifest V3 extensions.

  • Enhanced Security: This API allows approved extensions to register and execute custom scripts in an isolated environment while complying with Manifest V3 policies.
  • Developer Mode Requirement: For the userScripts API to function, users must explicitly enable "Developer Mode" in their browser extensions settings page (chrome://extensions).
  • Execution Limits: Scripts running via this API are strictly confined to DOM manipulation and standard web APIs, reducing their capability to access privileged extension APIs directly.

Shift to Background Service Workers

Manifest V2 allowed extensions to run persistent background pages that stayed active continuously. Manifest V3 replaces these with event-driven background service workers that terminate when idle.

This shift impacts userscripts in two primary ways:

  1. Startup Delays: When opening a webpage, the background service worker may need to "wake up," causing minor execution delays before custom scripts trigger.
  2. Loss of In-Memory State: Global variables stored in background memory reset whenever the worker goes idle. Userscripts relying on persistent background data must shift entirely to asynchronous storage solutions like chrome.storage.

Limitations on Network Interception

Under Manifest V2, advanced userscripts leveraged extension APIs like webRequest to modify HTTP headers, alter payload data, or redirect traffic dynamically.

Manifest V3 replaces blocking webRequest calls with declarativeNetRequest, requiring rule-based modifications defined in advance. As a result, userscripts that dynamically intercept, modify, or inject data into raw network requests on the fly face severe functional limits or may stop working altogether.

Summary of the User Impact

  • Manual Browser Setup: Users on Chromium browsers (Chrome, Edge, Brave, Opera) must turn on Developer Mode to allow userscript extensions to execute local code.
  • Script Incompatibilities: Complex scripts that rely on dynamic eval() execution, network modification, or persistent background tasks will require updates from their developers.
  • Alternative Browsers: Mozilla Firefox is adopting Manifest V3 with modifications that retain support for dynamic script execution and blocking webRequest capabilities, offering a more flexible environment for heavy userscript applications.
