How Userscripts Handle CORS Preflight Requests

Userscripts handle Cross-Origin Resource Sharing (CORS) preflight requests differently depending on whether they use standard web APIs or privileged userscript manager APIs. While standard fetch() or XMLHttpRequest calls executed within the page context trigger browser-enforced CORS OPTIONS preflight checks, specialized APIs like GM_xmlhttpRequest execute requests through the browser extension’s privileged background context. This background execution bypasses browser CORS enforcement entirely, preventing the browser from sending preflight requests to external servers.

Standard In-Page Requests vs. Privileged APIs

When a userscript uses standard JavaScript methods (window.fetch or window.XMLHttpRequest), the request runs directly inside the web page's security context. If the request attempts to access a cross-origin resource with custom headers, non-simple HTTP methods (like PUT or DELETE), or non-simple content types (like application/json), the browser automatically initiates a CORS preflight OPTIONS request. If the server does not explicitly allow the origin via Access-Control-Allow-Origin and related headers, the request fails.

To avoid these restrictions, userscript managers (such as Tampermonkey, Violentmonkey, and Greasemonkey) provide privileged network APIs, most notably GM_xmlhttpRequest (or GM.xmlHttpRequest in GM4+).

How GM_xmlhttpRequest Eliminates Preflights

GM_xmlhttpRequest bypasses CORS preflight checks through a specific mechanism:

  1. Context Switching: Instead of initiating the HTTP request from the web page's context, GM_xmlhttpRequest passes the request details across the extension bridge to the userscript manager's background process or service worker.
  2. Privileged Network Calls: Extension background scripts possess broader network permissions compared to standard web pages. When the extension executes the request, the browser treats it as a privileged extension request rather than a cross-origin web page request.
  3. No Preflight Sent: Because extension-level requests are exempt from same-origin policy restrictions, the browser sends the actual request directly without first dispatching an OPTIONS preflight request, regardless of headers or HTTP methods used.
  4. Response Delivery: Once the external server responds, the extension forwards the response data back to the userscript running in the page tab.

Implementing Privileged Requests

To use this mechanism, a userscript must explicitly request permission in its metadata block using the @grant directive:

// ==UserScript==
// @name         External Data Fetcher
// @match        https://example.com/*
// @grant        GM_xmlhttpRequest
// @connect      api.external-domain.com
// ==UserScript==

GM_xmlhttpRequest({
    method: "POST",
    url: "https://api.external-domain.com/data",
    headers: {
        "Content-Type": "application/json",
        "Custom-Header": "value"
    },
    data: JSON.stringify({ key: "value" }),
    onload: function(response) {
        console.log("Data received:", response.responseText);
    }
});

Security Controls with the @connect Directive

Although CORS preflight checks are bypassed, modern userscript managers enforce their own domain-level security layer using the @connect directive.

If a script attempts to call GM_xmlhttpRequest targeting a domain not listed in its @connect rules, the userscript manager prompts the user to manually grant or deny access to that domain. This ensures that while browser-level CORS preflights are avoided, users maintain explicit control over which external domains a script can communicate with.
