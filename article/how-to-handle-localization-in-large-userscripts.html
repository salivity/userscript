How to Handle Localization in Large Userscripts

Managing internationalization (i18n) natively in large userscripts requires a lightweight, scalable pattern that avoids the overhead of external dependencies. By leveraging native JavaScript features such as navigator.language, nested dictionary objects, dynamic string interpolation, and Proxy objects for safe fallbacks, you can implement a high-performance localization system. This article breaks down the best native strategies to structure, manage, and render localized strings seamlessly within your userscripts.

1. Detecting and Normalizing User Locales

Browser environments provide the user's preferred language via navigator.language or navigator.languages. To ensure consistency, normalize these locale strings to match your script's supported language codes (typically standard ISO 639-1 two-letter codes or full BCP 47 tags).

const getPreferredLanguage = (supportedLocales, defaultLocale = 'en') => {
  const userLocales = navigator.languages || [navigator.language || defaultLocale];
  
  for (const locale of userLocales) {
    const primaryCode = locale.split('-')[0].toLowerCase();
    
    // Exact match (e.g., 'zh-CN')
    if (supportedLocales.includes(locale)) return locale;
    // Primary language match (e.g., 'en' from 'en-US')
    if (supportedLocales.includes(primaryCode)) return primaryCode;
  }
  
  return defaultLocale;
};

2. Structuring the Localization Dictionary

Keep localization strings modular by organizing them into key-value maps per language. For large scripts, structure keys hierarchically based on UI modules or features.

const i18nStrings = {
  en: {
    settings: {
      title: "User Settings",
      save: "Save Changes"
    },
    messages: {
      welcome: "Hello, {name}!"
    }
  },
  es: {
    settings: {
      title: "Configuración de Usuario",
      save: "Guardar Cambios"
    },
    messages: {
      welcome: "¡Hola, {name}!"
    }
  }
};

3. Creating a Translation Function with Dynamic Variables

A centralized helper function resolves dot-notation keys (e.g., 'settings.title') and replaces dynamic placeholders (e.g., {name}) within strings.

class TranslationManager {
  constructor(translations, defaultLocale = 'en') {
    this.translations = translations;
    this.defaultLocale = defaultLocale;
    this.currentLocale = getPreferredLanguage(Object.keys(translations), defaultLocale);
  }

  setLocale(locale) {
    if (this.translations[locale]) {
      this.currentLocale = locale;
    }
  }

  t(path, variables = {}) {
    const getValue = (locale) => 
      path.split('.').reduce((obj, key) => obj?.[key], this.translations[locale]);

    // Fallback logic: Try active locale, then default locale, then return key path
    let template = getValue(this.currentLocale) || getValue(this.defaultLocale) || path;

    if (typeof template !== 'string') {
      return path;
    }

    // Replace dynamic placeholders like {variable}
    return template.replace(/\{(\w+)\}/g, (_, key) => variables[key] ?? `{${key}}`);
  }
}

// Usage instance
const i18n = new TranslationManager(i18nStrings, 'en');
console.log(i18n.t('settings.save')); // Output based on browser language
console.log(i18n.t('messages.welcome', { name: 'Alice' }));

4. Using Proxies for Fail-Safe and Type-Like Access

To avoid broken layouts caused by missing translation keys, you can wrap your translation engine in a JavaScript Proxy. This enables direct property lookups while seamlessly applying fallbacks when keys are missing.

function createI18nProxy(manager) {
  return new Proxy(manager, {
    get(target, prop) {
      if (prop in target) return target[prop];
      return (variables) => target.t(prop, variables);
    }
  });
}

const __ = createI18nProxy(i18n);

// Lookups automatically route through the fallback system
console.log(__('settings.title'));

5. Architectural Best Practices for Large Userscripts

  1. Keep Fallbacks Self-Contained: Always assign a complete fallback dictionary (such as English) so that if a translated string is absent, the UI displays readable text instead of empty elements or undefined errors.
  2. Bundle Modules during Development: If your userscript is built using tools like Rollup or Esbuild, separate your translation JSON/JS files per language during development and bundle them into a single script output for distribution.
  3. Lazy Load Extra Locales (Optional): For exceptionally large scripts, load primary strings inline and fetch secondary language dictionaries dynamically using GM.xmlHttpRequest or fetch only when activated by the user.
