How Userscripts Prevent Malicious @require Injection

Userscripts use the @require directive to import external JavaScript libraries, which introduces potential security risks like supply-chain attacks and malicious code injection. Userscript managers handle these threats primarily through local script caching at installation time, Subresource Integrity (SRI) hash verification, execution sandboxing, and strict repository moderation policies. These combined measures ensure that remote changes to third-party libraries do not automatically compromise a user's browser.

Local Caching at Installation

When a userscript containing a @require metadata block is installed, the userscript manager downloads the specified external library immediately and stores it locally. From that point on, the userscript executes the locally cached version of the library rather than fetching the live file from the remote server on every page load. Even if an attacker compromises the server hosting the third-party library later, existing users remain unaffected because their browser does not re-download the modified script.

Subresource Integrity Verification

To guarantee that the downloaded library matches the exact file intended by the developer, userscript managers support Subresource Integrity (SRI). Developers specify a cryptographic hash within the @require URL. During installation, the manager hashes the downloaded file and compares it against the specified hash. If the remote file has been altered or tampered with, the hashes will not match, and the userscript manager blocks the installation or execution of the script.

Privilege Scoping and Sandboxing

Code imported via @require runs in the same execution context and privilege level as the main userscript. Userscript managers control what this context can do through the @grant metadata directive:

  • Restricted Context (@grant none): The script and its @require dependencies run in a standard page sandbox without access to elevated browser APIs. Malicious code cannot access cross-domain requests, local storage APIs, or file systems beyond what standard web page scripts can reach.
  • Elevated Context (@grant APIs): If special functions like GM_xmlhttpRequest or GM_setValue are explicitly requested, the main script and its dependencies gain access to those capabilities. Userscript managers display these requested permissions during installation so users can evaluate the risk.

Repository Controls and Static Analysis

Major userscript distribution platforms implement additional safety layers before scripts reach users:

  • Disallowing External CDNs: Platforms like Greasy Fork require dependencies to be hosted directly on the platform or selected trusted domain whitelists, preventing developers from pointing to uncontrolled external servers.
  • Code Auditing: Automated scanning tools inspect uploaded libraries for dynamic code evaluation functions such as eval(), obfuscation, or unauthorized data exfiltration attempts. Scripts failing these security checks are flagged or removed.
