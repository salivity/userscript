How Userscripts Manipulate WebRTC P2P Connections

Userscripts customize website behavior by running user-defined JavaScript inside the browser context, allowing users to intercept, modify, and monitor WebRTC API calls responsible for peer-to-peer (P2P) connections. By leveraging techniques like method overriding (monkey patching) on global browser objects like RTCPeerConnection, userscripts can inspect SDP (Session Description Protocol) messages, filter ICE candidates, prevent IP address leaks, or alter media streams before P2P connections are established.

How Userscripts Intercept the WebRTC API

WebRTC relies on standardized JavaScript APIs embedded in modern web browsers, primarily window.RTCPeerConnection and navigator.mediaDevices.getUserMedia. Because userscripts execute within the page context (or access it via wrappers like unsafeWindow), they can redefine these native API functions before the host website initializes a P2P connection.

This technique is known as monkey patching. A typical userscript saves a reference to the original RTCPeerConnection constructor and replaces window.RTCPeerConnection with a custom wrapper function.

When the website calls new RTCPeerConnection(), the userscript's custom function executes first. This allows the script to:

  • Inspect configuration objects (such as STUN/TURN server details).
  • Wrap instance methods like createOffer, createAnswer, setLocalDescription, and setRemoteDescription.
  • Intercept events like onicecandidate and ondatachannel.

Key Techniques for P2P Manipulation

1. Intercepting and Filtering ICE Candidates

During connection setup, WebRTC gathers Interactive Connectivity Establishment (ICE) candidates to discover network paths between peers. These candidates often contain local and public IP addresses.

Userscripts can manipulate the onicecandidate event listener or the addIceCandidate method:

  • Privacy Protection: Scripts can check candidate strings for specific IP address formats and drop them, preventing the website or peer from discovering the user's local LAN IP or real public IP address.
  • Forcing Relay Connections: A script can strip host and server-reflexive candidates, forcing WebRTC to use TURN relay servers instead of direct peer connections.

2. Modifying SDP Offer and Answer Payload

WebRTC uses SDP payloads to negotiate media codecs, bandwidth, and connection parameters. Userscripts can intercept the promises returned by createOffer() or createAnswer(), modify the resulting SDP text string, and pass the modified string to setLocalDescription().

This enables scripts to:

  • Disable specific video or audio codecs.
  • Change maximum allocated bandwidth values.
  • Strip video/audio tracks entirely from the negotiation phase while keeping data channels active.

3. Spoofing or Modifying Media Streams

WebRTC handles real-time audio and video transfer. By wrapping navigator.mediaDevices.getUserMedia or navigator.mediaDevices.getDisplayMedia, a userscript can alter the media stream supplied to a WebRTC connection.

  • Canvas Injection: A userscript can capture an HTML5 canvas element, generate synthetic visuals, and replace the user's real webcam stream using canvas.captureStream().
  • Audio Manipulation: Audio streams can be routed through the Web Audio API to apply filters, voice modification, or mute audio channels selectively before transmission.

4. Data Channel Interception

WebRTC DataChannels allow arbitrary data transfer between peers (commonly used in P2P file sharing, browser games, and chat apps). Userscripts can override the createDataChannel method or the ondatachannel event handler.

By placing a wrapper around the RTCDataChannel.prototype.send method and the onmessage event listener, userscripts can:

  • Log incoming and outgoing raw data packets for debugging or analysis.
  • Inject, modify, or block data packets in real-time.
  • Automate responses to specific P2P data messages.

Scope and Limitations

While userscripts have full access to the browser's JavaScript environment, their manipulation capabilities are bound by client-side boundaries:

  • Page Context Limits: If a target site executes WebRTC logic inside a sandboxed iframe or a Web Worker, the userscript must explicitly target those contexts to intercept the API.
  • Protocol Limits: Userscripts modify browser-level API calls, not lower-level UDP/TCP network packets. Once an encrypted WebRTC connection is established, network packets travel directly between peers without passing through JavaScript hooks.
