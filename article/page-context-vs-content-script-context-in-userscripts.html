Page Context vs Content Script Context in Userscripts

Understanding the difference between page context and content script context is fundamental to developing userscripts using extension managers like Tampermonkey or Violentmonkey. The primary distinction lies in execution isolation: page context operates directly within the webpage's main execution environment with full access to the site's global variables, while content script context executes in a sandboxed, isolated environment that has full access to privileged userscript APIs and shares only the Document Object Model (DOM) with the page.

What is Page Context?

The page context—often referred to as the "main world"—is the environment where the website's own JavaScript code runs. When code executes in the page context, it interacts directly with the site's native execution thread.

Key characteristics of the page context include:

  • Full Global Access: The script can access, modify, and invoke global variables, functions, and libraries defined by the host website (such as window.siteConfig or embedded libraries like React or jQuery).
  • Shared Memory: Modifications made to global objects directly alter the web page's runtime state.
  • Standard Web Security: Scripts in this context are restricted by standard browser security models, including Same-Origin Policy (SOP) and Content Security Policy (CSP). They cannot use privileged userscript functions like cross-domain requests.

What is Content Script Context?

The content script context—often referred to as the "isolated world"—is a private execution environment created by the userscript manager specifically for running user scripts.

Key characteristics of the content script context include:

  • Isolated JavaScript Scope: The script has its own distinct window object. Variables declared here do not leak into the web page's global scope, preventing conflicts with site scripts.
  • Shared DOM Access: While the JavaScript execution environments are separated, the script shares the DOM tree with the web page. It can freely modify HTML elements, attach event listeners, and alter CSS styles.
  • Privileged API Access: Scripts in this context can request elevated permissions, granting access to userscript APIs (such as GM_setValue, GM_getValue, and GM_xmlhttpRequest) that can bypass restrictions like cross-origin policies.

Key Differences Summary

  • DOM Access: Both contexts share full access to the DOM tree.
  • JavaScript Scope: Page context accesses the website's global window scope. Content script context operates in a separate global scope isolated from the webpage scripts.
  • Privileged APIs: Content script context can use GM_* APIs. Page context cannot use GM_* APIs.
  • Detection & Security: Content script context prevents the website from easily overriding or detecting script variables. Page context makes script variables directly visible to the website.

Bridging the Contexts

Userscripts frequently need to interact with page context variables while using content script features.

To read or call page-defined variables from an isolated content script, developers use unsafeWindow, an object provided by userscript managers that points to the page context's window object. Conversely, to execute code directly inside the page context, a userscript can dynamically inject a <script> tag into the DOM.

The context a script runs in is largely determined by its header metadata:

  • @grant none: Runs the script directly in the page context (or an unprivileged context), allowing direct access to page variables without using unsafeWindow.
  • @grant GM_getValue (or other GM APIs): Tells the manager to run the script inside the isolated content script context to safely expose privileged APIs.
