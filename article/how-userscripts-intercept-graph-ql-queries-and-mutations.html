How Userscripts Intercept GraphQL Queries and Mutations

Userscripts manipulate web applications directly in the browser, allowing developers to monitor, log, or modify network requests before they reach the server or after responses return. Because GraphQL operations typically rely on standard web transport APIs like fetch or XMLHttpRequest (XHR), userscripts achieve interception by monkey-patching these built-in browser methods. This guide breaks down the core mechanisms userscripts use to detect, read, and alter GraphQL queries, mutations, and responses.

Target Mechanisms: Patching Web APIs

GraphQL queries and mutations are usually sent via HTTP POST requests containing a JSON payload with query, variables, and operationName fields. To intercept these requests, a userscript must hook into the API the web application uses to execute HTTP requests.

1. Intercepting window.fetch

Most modern web applications use the fetch API. A userscript overrides window.fetch with a custom function while preserving a reference to the original implementation.

When a request is initiated:

  1. The userscript's wrapper function intercepts the URL and request options (such as headers and body).
  2. The script parses the request body to check if it contains a query or mutation string or an operationName.
  3. If it matches a targeted GraphQL operation, the userscript can modify the payload (e.g., changing query variables) before passing the arguments to the original fetch call.

2. Intercepting XMLHttpRequest (XHR)

For applications utilizing XHR, userscripts patch XMLHttpRequest.prototype.open and XMLHttpRequest.prototype.send.

  1. open() Patching: Stores request metadata, such as the HTTP method and target URL.
  2. send() Patching: Captures the outgoing request body. If the body contains a GraphQL JSON payload, the script can inspect or alter the payload prior to calling the original send method.

Identifying GraphQL Traffic

Because many applications use a single generic endpoint (e.g., /graphql), URLs alone may not distinguish one operation from another. Userscripts identify specific queries and mutations by inspecting the request body structure:

  • Operation Name: Checked via payload.operationName to identify specific operations (e.g., GetUserProfile).
  • Query Contents: Evaluated via payload.query using regular expressions or string matching to detect whether the operation is a query or a mutation.

Intercepting and Modifying GraphQL Responses

To modify data returned by a GraphQL query or mutation, the userscript hooks into the response handling pipeline.

  • With fetch: The wrapped function waits for the original fetch promise to resolve. It clones the response using response.clone(), extracts the JSON payload, alters the data property, and resolves the promise with a new Response object constructed from the modified payload.
  • With XHR: The script overrides the onreadystatechange or onload event listeners on the XMLHttpRequest instance, modifying the responseText or response property before the application's callback functions execute.

Context Execution and Timing

Browser extensions and userscript managers run scripts in isolated execution contexts (sandboxes) for security. If a userscript patches window.fetch inside its isolated scope, it will not catch network calls made by the main application context.

To ensure interception works properly:

  • unsafeWindow Access: Scripts use unsafeWindow.fetch or unsafeWindow.XMLHttpRequest to patch the page's native global scope directly.
  • DOM Script Injection: The userscript creates a <script> element containing the interceptor code and appends it to document.head or document.documentElement.
  • Execution Timing: Setting the userscript to run at @run-at document-start ensures the interception logic runs before the web page executes its own scripts and establishes network calls.
