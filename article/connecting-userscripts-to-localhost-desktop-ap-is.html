Connecting Userscripts to Localhost Desktop APIs

Yes, userscripts can communicate with external desktop applications using localhost APIs hosted on your local machine. This capability enables browser extensions and userscripts to trigger local actions, control desktop software, or retrieve system data directly from the web browser. This article covers how this connection works, the differences between standard browser APIs and userscript privileges, security considerations, and best practices for establishing communication.

How Communication Works

Desktop applications can host a lightweight local HTTP or WebSocket server listening on loopback addresses like http://localhost:PORT or http://127.0.0.1:PORT. Userscripts executed by extension managers like Tampermonkey, Violentmonkey, or Greasemonkey can send requests to these local endpoints to send commands or exchange data.

There are two primary methods for making these requests:

1. Standard Browser APIs (fetch or XMLHttpRequest)

Userscripts can use standard web APIs like fetch() to send HTTP requests to a local server. However, requests made this way are strictly governed by the browser's Same-Origin Policy (SOP) and Cross-Origin Resource Sharing (CORS) rules.

  • CORS Requirement: The desktop app’s local HTTP server must explicitly include CORS headers in its responses, such as Access-Control-Allow-Origin: * or specific origins, along with handling preflight OPTIONS requests.
  • Private Network Access (PNA): Modern browsers restrict public websites from making subresource requests to local endpoints (127.0.0.1 or localhost). If a userscript runs on a public website (e.g., https://example.com), standard fetch requests to localhost may be blocked by browser PNA security policies.

2. Userscript-Specific APIs (GM_xmlhttpRequest)

Userscript managers provide elevated privilege functions like GM_xmlhttpRequest (or GM.xmlHttpRequest) that execute requests outside the web page's standard sandboxed context.

  • Bypassing CORS and PNA: GM_xmlhttpRequest bypasses browser CORS restrictions and Private Network Access checks, making it the most reliable method for connecting to local desktop applications.
  • Metadata Configuration: To use this feature, the userscript must request permission in its header block using @grant and specify the local host using @connect:
// ==UserScript==
// @name         Desktop App Connector
// @namespace    http://tampermonkey.net/
// @version      1.0
// @match        https://example.com/*
// @grant        GM_xmlhttpRequest
// @connect      127.0.0.1
// @connect      localhost
// ==UserScript==

GM_xmlhttpRequest({
    method: "POST",
    url: "http://127.0.0.1:8080/api/action",
    headers: {
        "Content-Type": "application/json"
    },
    data: JSON.stringify({ command: "doSomething" }),
    onload: function(response) {
        console.log("Desktop app response:", response.responseText);
    },
    onerror: function(error) {
        console.error("Connection failed:", error);
    }
});

3. WebSockets (WebSocket)

For real-time, two-way communication, desktop apps can host a WebSocket server on ws://127.0.0.1:PORT. Userscripts can initialize a standard new WebSocket("ws://127.0.0.1:PORT") connection to stream data back and forth without polling HTTP endpoints repeatedly.

Security Best Practices

Allowing browser scripts to interact with local desktop applications introduces security risks. Malicious websites could attempt to send unauthorized requests to your local API if it is left unprotected.

  • Implement Authentication: Use an API key, bearer token, or unique session token generated by the desktop app that the user must copy into the userscript settings.
  • Validate Origin Headers: Check incoming Origin headers on the local server to verify where requests originate when using standard HTTP/WebSocket APIs.
  • Restrict Actions: Ensure the local API only exposes necessary operations and does not allow arbitrary system command execution without user confirmation.
