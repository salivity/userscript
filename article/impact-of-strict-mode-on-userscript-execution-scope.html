Impact of Strict Mode on Userscript Execution Scope

Enabling strict mode in JavaScript userscripts fundamentally alters how code is evaluated, variable scope is resolved, and execution context is bound. By placing "use strict"; at the top of a userscript or within specific functions, developers enforce rigid parsing and error-handling rules. This prevents accidental global scope pollution, modifies the binding of this, restricts access to execution context properties, and ensures cleaner isolation between the userscript sandbox and the host web page.

Prevention of Accidental Global Scope Pollution

In standard JavaScript, assigning a value to an undeclared variable implicitly creates a property on the global object. In the context of userscripts:

  • Without Strict Mode: Assigning myVar = 10; without let, const, or var attaches myVar to the execution sandbox's global scope or the page's window object (if running with @grant none).
  • With Strict Mode: Attempting to assign a value to an undeclared variable immediately throws a ReferenceError, stopping execution and preventing accidental leaks into the global namespace.

Altered this Binding

Strict mode changes how functions handle this when invoked without an explicit context:

  • Default Context: In non-strict mode, calling a standard function sets this to the global object (window or the sandbox wrapper).
  • Strict Context: In strict mode, this remains undefined for plain function calls. This prevents userscripts from accidentally reading or modifying global properties through an unanchored this.

Impact on Userscript Sandboxing and @grant Directives

Userscript managers (such as Tampermonkey or Violentmonkey) execute scripts in isolated environments based on their metadata directives:

  • @grant none: The script runs directly within the target page's execution context. "use strict"; safeguards the target website by preventing the script from overwriting host global variables or window properties.
  • Sandboxed Execution (e.g., @grant GM_getValue): The script executes within a wrapper or proxy sandbox. "use strict"; ensures variables remain local to the userscript scope and do not leak into the shared sandbox wrapper.

Scope Protection from Dynamic Expressions

Strict mode restricts language features that alter dynamic scoping:

  • Disallowance of with: The with statement is completely forbidden, eliminating dynamic scope lookup hazards.
  • eval() Scope Isolation: Variables declared inside an eval() block do not leak into the surrounding script or function scope, keeping the local execution scope clean.

Strict Interaction with unsafeWindow

When a userscript interacts with the host page via unsafeWindow:

  • Strict mode requires explicit variable assignment and prevents silent failures when writing to read-only properties on host objects.
  • Attempting to modify non-writable properties on unsafeWindow will throw a runtime error rather than failing silently, aiding in debugging security boundaries.
